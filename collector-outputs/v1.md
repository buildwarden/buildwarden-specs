# collector-outputs, version 1

The outputs a relay sends a collector to store, and the disk collector's layout of them.

| | |
|---|---|
| Seam | 2, the collector protocol: the outputs |
| Requirement identifiers | `COLLOUT-<n>` |
| Roles | collector, relay, disk collector (optional) |
| Concept | [The collector](https://buildwarden.github.io/buildwarden/concepts/architecture.html#collector-collector-library-cmdcollector-binary) in the BuildWarden book |
| Reference implementation | The disk collector, `cmd/collector` with `collector/`; the relay side in `relay/`, in [buildwarden/buildwarden](https://github.com/buildwarden/buildwarden) |
| Status | Not yet released. While its release is `v0.x.y` this document may still change incompatibly; see Versioning |

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY" and "OPTIONAL" in this
document are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174)
when, and only when, they appear in all capitals. A requirement is a
paragraph or list item that starts with its identifier in bold.

## Scope and roles

This document specifies the outputs of a build that a relay streams to its
collector: the artifacts the build posts, the payloads the relay captures,
the ledger, the environment record's payload and the build's console. It
says what a collector accepts, what it replies and in what order, which is
normative for every collector. Where a collector keeps the outputs is its
own, with one exception: a collector that writes them to a directory, as the
reference disk collector does, keeps the layout that `warden inspect` reads,
which **The disk collector's layout** below specifies and other collectors
need not meet.

The inputs and signals a collector serves the same relay (the build script,
the bootstrap config, the build context, and the `ready`, `heartbeat` and
`complete` signals) are the other specification of this seam,
`collector-inputs`. The ledger's own format is specified in
[buildwarden/buildwarden under `specs/build-ledger/`](https://github.com/buildwarden/buildwarden/tree/main/specs/build-ledger);
this document treats the ledger as a stream of bytes.

The machine-readable description of these endpoints is
[`v1.openapi.json`](v1.openapi.json), beside this document. Where it and a
requirement here differ, the requirement stands.

### The session

Seam 2 is one seam, the collector protocol, written as two specifications:
`collector-outputs`, the outputs a collector stores, and `collector-inputs`,
the inputs and signals it serves. Each has its own requirement prefix, its
own suite and its own releases, so a collector may implement one of them and
claim it. Nothing on the wire tells them apart: the claim names one
collector, and a relay sends the requests of both to it. Five subsections are
stated alike in the two documents, but for the prefix of their identifiers,
and change together: this one, *HTTP, and where the collector is*,
*Authentication*, *Names in paths*, and *D8* under Known divergences.

The roles are the same in both. The *collector* serves the protocol. The
*relay* is the only client of it: no other party sends a request that this
protocol specifies. Who starts a collector, and where it runs, is outside the
protocol.

**COLLOUT-1.** The protocol's unit is the build *session*: the requests of one
build, which a collector tells apart by the collector token they carry (see
Authentication). A collector MUST apply every rule of this document to each
session on its own. A collector that is given no token has exactly one
session.

**COLLOUT-2.** A session's completion, its first `POST /v1/complete` (which
`collector-inputs` specifies), is terminal. Once a collector has received it,
the collector owes the relay nothing more for that session, and it MAY close
the connection the session's requests arrive on at once, before it replies to
any of them.

How many sessions one instance of a collector serves is the collector's own.
A collector declares it in its target file.
The reference disk collector, `cmd/collector`, serves exactly one session and
then exits, with status 0 when the completion's `exit_code` is 0 and 1
otherwise. A collector that serves several sessions, and any side of a
collector that faces its own clients (opening a session, supplying inputs,
watching the console and the status, fetching the outputs), is outside this
version of the protocol.

## Transport

<!-- collector-common: begin -->
### HTTP, and where the collector is

The relay reaches the collector at the base URL the claim names, its
`collector_url` (`relay-claim`, Messages and fields). The value
`http://collector.tunnel` selects the tunnel the claimant opened on the
relay's claim endpoint, which carries HTTP/2 with prior knowledge and no TLS
with the relay as the client (`relay-claim`, Transport). Any other value is a
base URL that the relay dials itself, with HTTP as its scheme allows.

**COLLOUT-3.** A collector MUST serve each endpoint of this document at the
path this document gives it, appended to the base URL the claim names, over
HTTP: over the tunnel when the claim selects it, and otherwise at that base
URL.

**COLLOUT-4.** The relay MUST send every request of a session to the base URL
its claim named, with the path appended to it once any trailing `/` of the
base URL is removed.

### Authentication

**COLLOUT-5.** Where a session has a token, a collector MUST require it on
every request to an endpoint under `/v1/` that this protocol specifies, except
`GET /v1/status`. It MUST answer a request that carries no token, or another
one, with 401 and the body `unauthorized` followed by a line feed, whatever
the request's method, name or body, its path being one that a relay may send
(COLLOUT-12).

**COLLOUT-6.** A collector MUST NOT require a token for `GET /healthz` or for
`GET /v1/status`.

**COLLOUT-7.** A collector MUST accept the token in the `Authorization` header
in the form `Bearer <token>`, with one space after `Bearer`.

**COLLOUT-8.** A collector that has no token MUST NOT refuse a request for what
its `Authorization` header holds or lacks.

**COLLOUT-9.** When the claim's `collector_token` is not empty, the relay MUST
send `Authorization: Bearer <token>` on every request of the session. When it
is empty, the relay MUST send no `Authorization` header.

**COLLOUT-10.** A collector SHOULD compare a request's token with the
session's in a time that does not depend on how much of it matches.

## Messages and fields

<!-- collector-common: begin -->
### Names in paths

Some endpoints carry a name in their path: an artifact's name and a capture's
in `collector-outputs`, a context path in `collector-inputs`. A name is the
part of the path after the endpoint's prefix, as the collector reads it once
the path is percent-decoded.

**COLLOUT-11.** A name is *safe* when it is a relative slash path of 1 to 255
bytes, none of whose segments is empty, `.` or `..`, and whose bytes are all
in `[A-Za-z0-9._-]` or are the `/` between segments, and when it also keeps
the rule its own document adds for that kind of name. A collector MUST NOT
store, serve or list anything under a name that is not safe by its own
document's rule for it.

**COLLOUT-12.** The relay MUST percent-encode each segment of a name it
carries in a path, and MUST NOT send a path in which `//`, `/./` or `/../`
occurs or that ends in `/.` or `/..`. What a collector answers to such a path
is not specified by this version, whether or not the request carries the
token. The disk collector answers it, before it looks at the token, with 307
and a `Location` that is the path with those segments resolved.
<!-- collector-common: end -->

### The endpoints

| Endpoint | Body | Success |
|---|---|---|
| `PUT /v1/artifacts/<name>` | An artifact the build posted, streamed | 200, empty |
| `PUT /v1/captures/<name>` | A captured payload, of no length in advance, with the declared trailer `Warden-Hash` | 200, empty |
| `PUT /v1/ledger` | The session's ledger, streamed for the whole build | 200, empty, once the body has ended |
| `PUT /v1/environment` | The environment record's signed payload | 200, empty |
| `POST /v1/output` | A piece of the build's console | 200, empty |

**COLLOUT-13.** A collector MUST accept `PUT /v1/artifacts/<name>`, whose
body is the bytes of the artifact the build posted under that name, and
answer 200 with an empty body once it has stored them. The relay streams the
body as the build sends it, so a collector MUST NOT require its length in
advance.

**COLLOUT-14.** An artifact's name is a safe name (COLLOUT-11) each of whose
segments also starts and ends with a letter or a digit. A collector MUST
answer 400 to `PUT /v1/artifacts/<name>` when the name is not such a name, and
store nothing for it. The empty name, `PUT /v1/artifacts/`, is not one.

What a collector does with a second artifact under a name it has stored is
not specified by this version; the disk collector's is under **The disk
collector's layout**.

**COLLOUT-15.** A collector MUST accept `PUT /v1/captures/<name>`, whose body
is a payload the relay captured, and answer 200 with an empty body once it
has stored it. It MUST read the body's hash from the request trailer
`Warden-Hash`, which is 64 hexadecimal digits, when the request declares that
trailer in its `Trailer` header field (COLLOUT-18). Whether it reads a
`Warden-Hash` trailer that the request did not declare is not specified by
this version: the disk collector does over HTTP/1.1, and over HTTP/2, where
its server keeps only the trailers a request declared, it does not, and the
capture is then one with no trailer (COLLOUT-17).

**COLLOUT-16.** A capture's name is the name the relay sent, with every byte
outside `[A-Za-z0-9._-]` replaced by `_`; a `/` is replaced too, so a capture's
name is always one segment. A collector MUST store a capture under the name
so made, and MUST answer 400 when the name it was sent is empty, is longer
than 255 bytes, or is made only of `.`.

**COLLOUT-17.** A collector MUST NOT store a capture whose request carries no
`Warden-Hash` trailer, or one that is not 64 hexadecimal digits, and MUST NOT
answer such a request with 200. The hash sent as a header and not as a
trailer does not count.

**COLLOUT-18.** The relay MUST declare the trailer in the request's header
field `Trailer: Warden-Hash`, MUST send a capture's body with no length in
advance (chunked over HTTP/1.1; over HTTP/2, with the trailer in a `HEADERS`
frame that ends the stream), and MUST send the trailer `Warden-Hash` holding
the BLAKE2b-256 hash (unkeyed, 32 bytes) of exactly the bytes of the body, as
64 lower-case hexadecimal digits. The hash is the relay's statement about
the body. Two captures with the same hash are the same content.

**COLLOUT-19.** A collector MUST accept `PUT /v1/ledger`, whose body is the
session's ledger, written as the relay produces it for the whole of the
build, and answer 200 with an empty body once the body has ended and has
been stored.

**COLLOUT-20.** A collector MUST accept `PUT /v1/environment`, whose body is
the payload of the ledger's environment record, the bytes the relay signed,
and answer 200 with an empty body once it has stored them. It MUST answer 405
to any other method on this path, `POST` among them. The relay sends the body
with no `Content-Type`.

**COLLOUT-21.** A collector MUST accept `POST /v1/output`, whose body is a
piece of the build's console, and answer 200 with an empty body once it has
stored it. It MUST keep the pieces of a session as one stream, in which a
piece whose request began after the reply to another piece's request follows
that piece. The order of pieces whose requests overlap, and whether their
bytes interleave, is not specified by this version. Where one piece ends and
the next begins carries no meaning.

**COLLOUT-22.** The relay MUST send each output with the method the table
gives it: `PUT` for artifacts, captures, the ledger and the environment, and
`POST` for the console.

**COLLOUT-23.** On `/v1/artifacts/<name>`, `/v1/captures/<name>` and
`/v1/ledger` a collector MUST answer 405 to a method other than `PUT` and
`POST`, and on `/v1/output` to a method other than `POST` and `PUT`. What it
does with the second method of each pair is not specified by this version (it
is D3, under Known divergences).

**COLLOUT-24.** A collector MUST answer a request with a status other than
200 when it has not stored the output the request carries, for a reason of
its own (a full disk, a failed write) as for the ones this document names.

**COLLOUT-25.** The relay MUST read only 200 as an output stored, and any
other status, or a request that fails, as an output not stored.

## Ordering

**COLLOUT-26.** The relay MUST open `PUT /v1/ledger` before it sends any
other output of the session, and MUST send exactly one ledger request in a
session.

**COLLOUT-27.** When the claim carries an environment, the relay MUST send
`PUT /v1/environment` once, and before the ledger's environment record: the
collector holds the payload before the ledger states its hash.

**COLLOUT-28.** A collector MUST serve the session's other requests while its
`PUT /v1/ledger` is open: the ledger request lasts for the whole build.

**COLLOUT-29.** Before it sends the session's `POST /v1/complete`
(`collector-inputs`), the relay MUST end the ledger request's body and wait
for that request's reply or its failure. Every output the relay sends for a
request of the build that ended before the build signalled its end MUST have
been answered by then.

What the relay does with a request the build makes after its end is the
relay's guest API (`relay-guest-api`), and after completion the collector
owes the relay nothing (COLLOUT-2).

## Errors

A collector's replies, by status. Each is stated by the requirements named.

| Status | When | Requirements |
|---|---|---|
| 200 | The output is stored; the body is empty | COLLOUT-13, COLLOUT-15, COLLOUT-19, COLLOUT-20, COLLOUT-21 |
| 400 | An artifact's name that is not safe, or a capture's that is empty, too long or only dots | COLLOUT-14, COLLOUT-16 |
| 401 | A session's token is missing or wrong | COLLOUT-5 |
| 405 | A method the endpoint does not take | COLLOUT-20, COLLOUT-23 |
| 413 | A body over the collector's limit | COLLOUT-30 |
| Any but 200 | A capture with no valid `Warden-Hash` trailer; an output the collector could not store | COLLOUT-17, COLLOUT-24 |

But for the 401's (COLLOUT-5), the body of a reply other than 200 is text for a
person, which this version does not specify and no relay reads. A path this
protocol does not specify is outside it. The disk collector answers 404 to one
under `/v1/`, but for `/v1/artifacts`, `/v1/captures` and `/v1/context` with no
trailing `/`, which it answers, before it looks at the token, with 307 and a
`Location` that is the same path with one.

## Limits

**COLLOUT-30.** A collector's limits on the size of a body are its own. A
collector MUST answer 413 to a request whose body exceeds one of them, and
MUST NOT store an artifact, a capture or an environment payload whose body
exceeded it.

**COLLOUT-31.** A collector MUST accept an environment payload of up to
1 MiB (1,048,576 bytes), and the relay MUST NOT send a larger one. A collector
MAY refuse a larger one with 413.

The relay's own limits on what the build may send it, an artifact's size
among them, are the relay's guest API (`relay-guest-api`). The disk
collector's limits are under **The disk collector's layout**.

## The disk collector's layout

This section is what a collector that writes a session's outputs to a
directory keeps: the layout `warden inspect` reads. A collector that keeps
them anywhere else need not meet it. Each path is relative to the session's
output directory.

| Endpoint | Stored as |
|---|---|
| `PUT /v1/artifacts/<name>` | `artifacts/<name>` |
| `PUT /v1/captures/<name>` | `payloads/<hash>`, and `captures/<name>` referring to it |
| `PUT /v1/ledger` | `ledger` |
| `PUT /v1/environment` | `environment.json` |
| `POST /v1/output` | `build-output.log` |

**COLLOUT-32.** A disk collector MUST store an artifact at
`artifacts/<name>`, creating the directories its name's segments name. A
request that does not end in 200 MUST NOT leave at that path the part of its
body that arrived.

**COLLOUT-33.** A disk collector MUST store a capture's body at
`payloads/<hash>`, `<hash>` being the trailer's value as sent (so that two
hashes that differ only in the case of their letters are two payloads), and
MUST make `captures/<name>` refer to it: a symbolic link to
`../payloads/<hash>`, or, where it cannot create one, a copy of the payload. Content that is already
stored under its hash MUST NOT be stored a second time.

**COLLOUT-34.** A disk collector MUST write the ledger to `ledger` as its
bytes arrive. If the request ends early, the bytes that arrived MUST be kept:
every record of the ledger is signed, so a ledger cut short verifies up to its
last whole record.

**COLLOUT-35.** A disk collector MUST store the environment payload at
`environment.json`, byte for byte. A request that does not end in 200 MUST
NOT leave there the part of its body that arrived.

**COLLOUT-36.** A disk collector MUST append each piece of the console to
`build-output.log`, in the order of COLLOUT-21.

A second artifact under a name replaces the first: the disk collector
truncates `artifacts/<name>` when the second request begins, and removes it
when that request does not end in 200, so that neither is left. It appends
each piece of the console as its bytes arrive, without waiting for another
request to end, so pieces whose requests overlap may interleave.

The directory may also hold files that are not outputs of this protocol. The
BuildWarden session that claims the relay writes the relay's CA certificate
there as `ca.cert.pem`, and `warden` may compress `ledger` and `ca.cert.pem`
once the build is over. While a capture arrives, the disk collector lands it
in a temporary file in `payloads/`, whose name starts `incoming-`, and
renames it once the hash is known.

The disk collector's limit is 4 GiB for each request's body on
`/v1/artifacts/`, `/v1/captures/`, `/v1/ledger` and `/v1/output` (the
library's `MaxArtifactBytes`, 4 GiB unless the embedding program sets
another), and 1 MiB for the environment payload. When the ledger or a piece
of the console passes its limit, what arrived before the limit stays in
`ledger` or `build-output.log`.

## Versioning

This is version 1 of the protocol, the one whose paths start `/v1/`. A
release of this specification is a tag `collector-outputs/vX.Y.Z` of the
specifications repository, and its `CHANGELOG.md` says what each changed.
While the release is `v0.x.y`, this document is edited in place and may still
change incompatibly. From `collector-outputs/v1.0.0` on, version 1 changes only
compatibly, and an incompatible change is a new document, `v2.md`, with its
own paths.

The part this document states alike with `collector-inputs` (the session,
the transport, authentication and the names in paths) changes in both
documents together, and is released as a new version of each.

## Conformance

A collector conforms to this specification when it meets the requirements
of the *collector* role:

- COLLOUT-1, COLLOUT-2, COLLOUT-3, COLLOUT-5, COLLOUT-6, COLLOUT-7, COLLOUT-8,
  COLLOUT-10 and COLLOUT-11;
- COLLOUT-13 to COLLOUT-17, COLLOUT-19 to COLLOUT-21, COLLOUT-23 and
  COLLOUT-24;
- COLLOUT-28, COLLOUT-30 and COLLOUT-31.

A collector that writes the outputs to a directory may also claim the *disk
collector* role, which adds COLLOUT-32 to COLLOUT-36.

A relay conforms to this specification when it meets the requirements of the
*relay* role: COLLOUT-4, COLLOUT-9, COLLOUT-12, COLLOUT-18, COLLOUT-22,
COLLOUT-25 to COLLOUT-27, COLLOUT-29 and COLLOUT-31.

A requirement that no case of this specification's suite checks is listed,
with the reason, in [`not-machine-checked.txt`](not-machine-checked.txt).

## Known divergences

Where the reference implementation differs from a rule or a comment of its
own repository, or from the rest of this protocol. Each is what the code on
`main` does, and this document allows it, but for N13 and N31; none is to be
relied on. The numbers D2, D3, D4 and D8 are those of the design that
wrote this specification. N13, N15, N27 and N31 are not yet in that design's table; the
N numbers are shared by the six documents, and N13 and N27 are recorded
in `collector-inputs` too. The line numbers are those of
buildwarden/buildwarden at `623131a`, where the files they name are as
they were at `3cb0b2b`.

### D2, a capture with no hash is a server error

The disk collector answers 500 to a capture whose `Warden-Hash` trailer is
missing or is not 64 hexadecimal digits, where every other request that is
wrong is answered with a 4xx status. COLLOUT-17 asks only that such a
capture is not stored and not answered with 200.

### D3, the methods on four endpoints

The disk collector accepts `POST` on `/v1/artifacts/<name>`,
`/v1/captures/<name>` and `/v1/ledger`, where the protocol has `PUT`, and
`PUT` on `/v1/output`, where it has `POST`, and treats each as the method the
protocol names. Its own replies to other methods on those paths say
`PUT only` and `POST only`. `/v1/environment` alone takes `PUT` and nothing
else (COLLOUT-20). COLLOUT-23 leaves the second method of each pair
unspecified, so that a collector may accept it or refuse it.

### D4, the capture's hash is not checked

The disk collector stores a capture under the hash the trailer names and
does not compute the hash of the body itself. The hash is the relay's
statement (COLLOUT-18): this version does not ask a collector to check it,
and a payload stored under a hash that is not its own is the relay's fault.

<!-- collector-common: begin -->
### D8, the token with no scheme

COLLOUT-7 asks a collector to accept `Authorization: Bearer <token>`, which is
the header every relay sends (COLLOUT-9). The disk collector also accepts the
token with no scheme: it removes exactly `Bearer ` from the front of the
header when it is there, and compares what is left with the token. So
`Authorization: <token>` passes, while `bearer <token>` and `Bearer  <token>`,
with two spaces, do not. The Go relay's claim endpoint accepts the same bare
token in its own way (`relay-claim`, Known divergences), and the two differ
from each other in what spacing they take. A suite does not assert which
scheme a collector accepts beyond COLLOUT-7.
<!-- collector-common: end -->

### N13, the relay follows a collector's redirects

Not yet in the design's table (found 3b).

The Go relay's collector client is an `http.Client` with no redirect
policy of its own (`relay/collector_client.go:42`), so it follows a
collector's 301, 302, 303, 307 and 308 replies, up to ten, with the token
kept on the same host, and a 301, 302 or 303 turned into a `GET`. It then
reads the status of the request it was redirected to. This differs from
COLLOUT-25, under which only the collector's own 200 is read as an output stored, and from the
collector as the relay's one source of inputs and one destination of
outputs. Seen against the Go relay at `3cb0b2b`: a 302 on
`GET /v1/build-script` was followed and its target's 200 body `SCRIPT`
served as the script; a 307 on `POST /v1/ready` and a 308 on
`PUT /v1/environment` were followed, each with the `Bearer` token.

### N15, a capture's name may be longer than a collector takes

Not yet in the design's table (found 3b).

The Go relay names a capture from its sequence number, the method, the
request's host and up to 80 bytes of its path (`relay/relay.go:903-914`,
`relay/capture.go:92`), and bounds neither the host nor the whole. A host
long enough makes a name over 255 bytes, which a collector refuses with
400 (COLLOUT-16): the capture is not stored, and the relay logs one line
(`relay/capture.go:86-89`) and goes on, when the refusal does not end the
tunnel (N31). This version has no requirement
on the length of the name a relay sends; it differs from the relay as
the one that streams every output it records to the collector. Read from
the code (`captureBaseName`, and `sanitizeCaptureName` at
`collector/paths.go:66-67`); not run.

### N27, a path with a dot segment or `//` is redirected, not refused

Not yet in the design's table (found 3b).

The disk collector's handlers sit behind Go's `http.ServeMux`
(`collector/collector.go:171-183`), which answers a path with a `.` or
`..` segment, or `//`, with 307 to the path cleaned, before the handler or
the token check sees it, and does the same for `/v1/artifacts` and
`/v1/context` with no trailing `/`. The design's seam 2 has 400 for an
unsafe artifact name and 403 for an unsafe context path; COLLOUT-12 and COLLOUT-14 state what
the code does, and COLLOUT-12 forbid a relay to send such a path. Seen against the
disk collector at `3cb0b2b`: `PUT /v1/artifacts/a/../b` got 307 to
`/v1/artifacts/b`, `GET /v1/context/sub/../sub` got 307, and
`a/%2e%2e/b` got 400.

### N31, a capture answered before its body has ended ends the tunnel

Not yet in the design's table (found 8b).

The disk collector serves the tunnel with `golang.org/x/net/http2`'s
`Server.ServeConn` (`relaycfg/tunnel.go:58-59`), and answers some
captures before it reads their body: 400 for a name it refuses
(`collector/collector.go:242-244`), and 401 for a token it refuses
(`:177`). A capture's trailer `Warden-Hash` (COLLOUT-18) then arrives on
a stream the server has answered, which that server takes for a
connection error, `PROTOCOL_ERROR`: it ends the tunnel, and with it the
open `PUT /v1/ledger` and every request of the session after it. A
refused capture should cost the relay that capture only (COLLOUT-25); it
can cost the session, which breaks COLLOUT-28. The Go relay sends a
capture whose name the collector refuses when the request's host is
long (N15). Seen against the disk collector at `623131a`: of four
sessions that each sent one capture with a refused name and then five
pieces of console, three served the five pieces and one answered none,
the tunnel having closed, its log saying `http2: server connection
error ... PROTOCOL_ERROR`; a probe of `x/net/http2` alone, a server and
a client as `relaycfg/tunnel.go` makes them, ended its connection
within ten such requests. The harness's own collector is served the
same way and does the same, so a suite sends nothing on a session after
a capture it expects refused.
