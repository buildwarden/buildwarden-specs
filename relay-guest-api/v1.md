# relay-guest-api, version 1

What a relay serves the build it isolates: DHCP, DNS, the reserved hosts, the control plane and interception.

## Scope and roles

A build runs in an isolated environment whose only network is a segment it
shares with its relay, the *build link*. Everything the build environment
reaches, it reaches through the relay: its address, its name resolution,
the build's inputs, the place its outputs go, and every upstream server.
This document says what the relay serves on the build link and how the
build environment uses it.

Two roles take part:

- The *relay* serves everything in this document, for one build.
- The *build environment* is the client: the executor that runs the build
  script, and the build's own tools. It is a role, defined by what it sends;
  this document names no component for it. In the reference implementation
  the executor is `warden-io`.

The relay serves, on the build link:

- the build environment's address lease (DHCP), where it serves one, and on
  a frame link the link layer below IP (ARP);
- DNS, which answers the two reserved names itself and forwards every other
  query;
- the reserved host `artifacts`: liveness, completion, the relay's
  certificate authority, the build script, the bootstrap config, and
  artifact uploads;
- the reserved host `cwd`: the build context;
- the control plane on port 8300: the relay's health, the certificate
  authority, the build's console output and its completion;
- for every other host, an HTTP proxy on port 80 and TLS interception on
  port 443, whose exchanges the relay records.

Outside this document:

- How a relay is claimed, and what the claim tells it about the build link,
  the upstream resolvers and the collector: that is `relay-claim`.
- What the relay sends to and fetches from its collector: that is
  `collector-outputs` and `collector-inputs`. This document names the
  collector's path where the relay serves or forwards what it carries.
- How the executor is started and in which order it uses this API: that is
  `executor-initialize`.
- The bootstrap config's format: that is `bootstrap-config`. This document
  says only how the relay carries it.
- On a kernel interface, how the build's connections to other addresses are
  brought onto the relay's ports: that is the driver's (seam 7). In the
  reference implementation the relay virtual machine's init redirects them
  (`tools/relay-vm/init`), and the container driver rewrites them in the
  build's network namespace.

The ledger the relay records to is specified in buildwarden/buildwarden
under
[`specs/build-ledger/v1.md`](https://github.com/buildwarden/buildwarden/tree/main/specs/build-ledger/v1.md),
with the metadata schemas of its records beside it. This document says which
exchanges the relay records, not how.

## Transport

**GUEST-1.** The relay MUST serve this API to the build environment over
IPv4, on the build link, at its own address on that link, *the relay's
address*: with a `build_link` (`relay-claim`), the link's relay address; in
a mode without one, the IPv4 address the relay already holds on the link (in
the Go relay's container mode, the first IPv4 address of its interfaces that
is not a loopback address). What a relay serves over IPv6 is not defined by
this version.

The reference implementation serves the build environment on one of two
kinds of link, by its mode (RELAY-04 in buildwarden/buildwarden):

- a *kernel interface*, in vm and container mode: the relay binds sockets
  of its operating system, and only traffic addressed to the relay's address
  reaches them unless the driver redirects it;
- a *frame link*, in host mode: the relay reads and writes the build
  environment's Ethernet frames on a socket it inherits, through a network
  stack of its own, and so is the build environment's whole network below
  IP.

A relay that is none of these modes states which kind of link it serves.

### On a kernel interface

**GUEST-2.** A relay on a kernel interface MUST serve, on the relay's
address: DNS on UDP port 53 and on TCP port 53; the HTTP proxy on TCP
port 80; TLS interception on TCP port 443; and the control plane on TCP
port 8300.

The Go relay binds those ports on every address it has, not only the
relay's address; what it serves on its other interfaces is not the build
environment's and not this document's.

### On a frame link

**GUEST-3.** A relay on a frame link MUST answer each ARP request for the
relay's address with an ARP reply that gives its own MAC address, and MUST
NOT answer an ARP request for any other address.

**GUEST-4.** A relay on a frame link MUST take the build environment's MAC
address from the source address of the first frame it receives, and send
its frames to that address. Until it has received a frame it sends them to
the broadcast address.

**GUEST-5.** A relay on a frame link SHOULD announce its own address from
the start of the link with gratuitous ARP, broadcast, since a build
environment may not treat the link as up before it receives a frame (a
macOS guest does not). The Go relay sends a gratuitous ARP reply for its
own address every 500 ms for the first 60 s.

**GUEST-6.** A relay on a frame link MUST accept a TCP connection to any
destination address and any destination port, and MUST select the service
by the destination port alone: port 443 is TLS interception, port 8300 the
control plane, and every other port but 53, 80 among them, the HTTP proxy.
A TCP connection to port 53 MAY be served as DNS over TCP (GUEST-12) or
reach the HTTP proxy; the Go relay sends it to the proxy (Known
divergences, D15). So on a frame link the build environment connects to
the addresses DNS gave it, and the relay captures the connections itself.

**GUEST-7.** A relay on a frame link MUST serve UDP only on port 53 of the
relay's address (DNS) and to the build environment's DHCP requests
(GUEST-8). It MUST NOT serve any other UDP port or address, MUST NOT
forward a datagram of the build environment's to any other host, and MUST
NOT answer a frame whose EtherType is neither ARP nor IPv4.

What a relay on a frame link answers in ICMP is not defined by this
version. The Go relay's network stack answers an ICMP echo request to the
relay's address with an echo reply, and none to any other address; and to
UDP for a port it does not serve, at the relay's address or at any other
address, it answers ICMP destination unreachable (port unreachable) whose
source is the address the datagram was sent to.

## Messages and fields

### The address lease

A relay serves the build environment's address lease on a frame link
always, and on a kernel interface where its claim carried a `build_link`
(`relay-claim`, which says which mode does what at the claim). The lease
gives the build environment the link's guest address. A build environment
that its launcher addresses itself does not need it.

**GUEST-8.** Where it serves the lease, the relay MUST answer every
DHCPDISCOVER with a DHCPOFFER and every DHCPREQUEST with a DHCPACK, from
UDP port 67 to UDP port 68 of the IPv4 broadcast address 255.255.255.255,
with the relay's address as the IPv4 source.

**GUEST-9.** Each OFFER and ACK MUST carry, in a BOOTP reply (RFC 2131):

| Field or option | Value |
|---|---|
| `op`, `htype`, `hlen` | 2 (BOOTREPLY), 1 (Ethernet), 6 |
| `xid` | The request's |
| `yiaddr` | The link's guest address |
| `siaddr` | The relay's address |
| `chaddr` | The request's first six bytes |
| The magic cookie | 99.130.83.99 |
| Option 53, message type | 2 (OFFER) or 5 (ACK) |
| Option 54, server identifier | The relay's address |
| Option 51, lease time | 4294967295, infinite (RFC 2131, section 3.3) |
| Option 1, subnet mask | The link's mask |
| Option 3, router | The relay's address |
| Option 6, domain name server | The relay's address |

The Go relay sends the options in the order of the table, then option 255,
in a reply padded to 300 bytes. On a frame link it addresses the Ethernet
frame to the request's `chaddr`.

**GUEST-10.** The relay MUST keep no lease state: it MUST give the same
answer to every DISCOVER and every REQUEST, whatever address the request
asks for and whatever client it names, and MUST NOT answer a REQUEST with a
DHCPNAK. So the build environment can only ever be told its own address,
and a flood of requests exhausts nothing.

**GUEST-11.** The relay MUST NOT answer any other DHCP or BOOTP message: a
BOOTREPLY, a DHCPDECLINE, DHCPRELEASE or DHCPINFORM, a message without the
magic cookie or without option 53, a message shorter than 240 bytes, or one
whose options are truncated.

### DNS

**GUEST-12.** The relay MUST serve DNS on port 53 of the relay's address
over UDP. A relay on a kernel interface MUST serve it over TCP as well
(GUEST-2). A relay on a frame link MAY serve it over TCP as well; the Go
relay does not (GUEST-6; Known divergences, D15).

**GUEST-13.** To a query for the name `artifacts` or `cwd` of type A, the
relay MUST answer itself with one A record of class IN for that name,
holding the relay's address, with TTL 0.

**GUEST-14.** To a query for `artifacts` or `cwd` of any other type, the
relay MUST answer itself with response code NOERROR and no answer records.

**GUEST-15.** The relay MUST forward every other query to its upstream
resolvers (`relay-claim`: the claim's `upstream_dns`, or the relay's
default) in their list order, asking the next resolver when one fails or
has not answered within 5 s, and MUST reply to the build environment with
the first answer a resolver gives, with the ID of the build environment's
query. It MUST NOT ask any resolver that is not on the list.

**GUEST-16.** When no resolver on the list answers, the relay MUST reply
with response code SERVFAIL.

### The reserved names

`artifacts` and `cwd` are names the relay serves itself, in DNS (GUEST-13)
and as HTTP hosts.

**GUEST-17.** The relay MUST route each HTTP request it receives on the
proxy's and the interception's ports by the request's target host,
ignoring a port in it: the host of the request's target when the target is
in absolute form (RFC 9112, section 3.2.2, which has the relay ignore the
`Host` field then), and otherwise the host part of the request's `Host`. A
request for `artifacts`, whatever its method, MUST be served as the
reserved host `artifacts`; a `GET` for `cwd` MUST be served as the
reserved host `cwd`; a request for `cwd` with any other method MAY be
proxied or answered otherwise, and the Go relay proxies it (Known
divergences, D10); and every other request MUST be proxied (GUEST-41).
This holds on port 443 as on port 80: inside the TLS connection it is the
request that decides, not the name the client sent at the handshake.
For both reserved hosts, the request's path is its target's path
percent-decoded (RFC 3986, section 2.1), without its query: the relay
matches the fixed paths, and applies GUEST-27, GUEST-28 and GUEST-33, to
the decoded path, and reads nothing of the query but `code` (GUEST-22). So
`GET /%68eartbeat` is the heartbeat, `POST /a%2Fb?x=1` stores the artifact
`a/b`, and `GET /%2e%2e/x` for `cwd` is refused.

**GUEST-18.** The build environment MUST spell the reserved names exactly
`artifacts` and `cwd`, in lower case, in its DNS queries and in each
request's target host, and without a trailing dot in the latter. (A name in
a DNS query is always absolute; the relay reads it without its root.) How
a relay treats any other spelling of them is not defined by this version.

### The reserved host `artifacts`

The build environment reaches `artifacts` as `http://artifacts/` on port 80,
or through interception on port 443. Its fixed paths are below; every other
path of a `POST` is an artifact's name.

| Request | Reply | Effect | Requirement |
|---|---|---|---|
| `GET /heartbeat` | 200, `ok` | Marks the build alive | GUEST-19, GUEST-20 |
| `POST /exit?code=<n>` | 200, `ok` | Completes the build with exit code `n`; terminal | GUEST-21, GUEST-22 |
| `GET /ca.pem` | 200, `application/x-pem-file` | The relay's certificate authority; not recorded | GUEST-23 |
| `GET /ca.crl` | 200, `application/pkix-crl` | Its empty CRL; not recorded | GUEST-24 |
| `GET /build-script` | 200, `application/octet-stream`; 404 | The build script; recorded | GUEST-25 |
| `GET /bootstrap` | 200, `application/json`; 404 | The bootstrap config; recorded | GUEST-26 |
| `POST /<name>` | 200; 400; 413; 500 | Stores an artifact; recorded | GUEST-27 to GUEST-30 |
| Anything else | 404, `not found` | | GUEST-32 |

**GUEST-19.** To `/heartbeat` the relay MUST answer `200` with
`Content-Type: text/plain` and the body `ok` and a line feed.

**GUEST-20.** The relay MUST count each `/heartbeat` and each request it
proxies (GUEST-41) as the build environment's activity, and send its
collector heartbeats (`collector-inputs`) by it, to these bounds: after an
activity, a first heartbeat within 2 s; then one at least every 2 s while
the latest activity is less than 4 s old; none once the latest activity is
5 s old or older, and none before there has been any. Between 4 s and 5 s
a heartbeat may be sent or not. The build environment SHOULD request
`/heartbeat` at least every 2 s while the build runs; the reference
executor does.

The Go relay keeps the time of the latest activity in whole seconds,
truncated, and checks it every 2 s on a ticker started when it starts: at
each tick it sends a heartbeat when that time is less than 5 s before the
tick. Its heartbeats are therefore 2 s apart and not aligned with the
activity, which is why the bounds above leave a second of slack.

**GUEST-21.** To `/exit` the relay MUST complete the build: it ends its
ledger, sends the whole ledger to its collector (`collector-outputs`), and
only then sends the collector the completion with the request's exit code
(`collector-inputs`), in that order; then it answers `200` with
`Content-Type: text/plain` and the body `ok` and a line feed. A failed
completion at the collector is the relay's to log and does not change the
reply. Completion is terminal (GUEST-55).

**GUEST-22.** The exit code is the query parameter `code`, a decimal
integer, optionally negative, from -9223372036854775808 to
9223372036854775807 (a signed 64-bit integer). The build environment MUST
send it so when it has an exit code. Without `code`, or with an empty one,
the exit code is 0. What a relay makes of any other value is not defined
by this version: the Go relay reads the longest leading decimal integer,
with an optional sign (`7x` is 7, `+5` is 5), and takes 0, which is
success, for a value it cannot read or one beyond its integer's range.

**GUEST-23.** To `/ca.pem` the relay MUST answer `200` with
`Content-Type: application/x-pem-file` and its certificate authority's
certificate (GUEST-48) as PEM: the same bytes as the claim reply's
`ca_cert` (`relay-claim`). It MUST NOT record it (GUEST-50).

**GUEST-24.** To `/ca.crl` the relay MUST answer `200` with
`Content-Type: application/pkix-crl` and the DER bytes of a certificate
revocation list that its certificate authority signed, that revokes
nothing, and whose next update is not before the end of the authority's
validity. It MUST serve the same bytes on every request, and MUST NOT
record them (GUEST-50). The Go relay's CRL has number 1, and its this-update
and next-update are its authority's not-before and not-after.

**GUEST-25.** To `/build-script` the relay MUST fetch the build script from
its collector (`GET /v1/build-script`, `collector-inputs`) and, when the
collector answers `200`, answer `200` with
`Content-Type: application/octet-stream` and the collector's bytes
unchanged, and record them (GUEST-49). When the collector has none
(`404`), it MUST answer `404`; the Go relay's body is
`build script unavailable` and a line feed.

**GUEST-26.** To `/bootstrap` the relay MUST fetch the bootstrap config from
its collector (`GET /v1/bootstrap`, `collector-inputs`) and, when the
collector answers `200`, answer `200` with `Content-Type: application/json`
and the collector's bytes unchanged, and record them (GUEST-49). When the
collector has none (`404`), it MUST answer `404`; the Go relay's body is
`no bootstrap config` and a line feed. The relay does not read the config:
its format, and what a `404` means to the executor, are `bootstrap-config`'s.

The Go relay also answers `404` to `/build-script` and to `/bootstrap` when
the collector answers any other status, or cannot be reached; this version
does not define the reply in that case.

**GUEST-27.** To a `POST` to any path but the fixed ones, the relay MUST
store the request's body as an artifact, whatever its `Content-Type`: its
name is the path (GUEST-17) without its leading `/`, and `unnamed` when
that is empty. The relay MUST stream the
body to its collector (`PUT /v1/artifacts/<name>`, `collector-outputs`) as
it receives it, record the artifact (GUEST-49), and answer `200` with
`Content-Type: text/plain` and the body
`artifact stored: <name> (<n> bytes)` and a line feed, where `<n>` is the
body's length in bytes in decimal.

**GUEST-28.** An artifact's name MUST be at most 255 bytes, MUST NOT start
or end with `/`, and MUST be one or more segments separated by `/`, each of
which consists only of ASCII letters, digits, `.`, `-` and `_`, does not
start with `.`, `-` or `_`, does not end with `.`, `-` or `_`, and is not
empty. The build environment MUST send only such names. To a name that
breaks this rule the relay MUST answer `400` with the body
`invalid artifact name` and a line feed, and store and record nothing.

**GUEST-29.** To an artifact whose body exceeds 2 GiB (2147483648 bytes) by
more than one byte the relay MUST answer `413` with the body
`artifact size limit exceeded` and a line feed, and to one of 2 GiB and one
byte it SHOULD; the Go relay stores that one (Known divergences, N33). When
the collector does not store the artifact, the relay MUST
answer `500`; the Go relay's body is `storage error`, with no line feed. In
either case the artifact is not recorded as stored. The build environment
MUST NOT send an artifact larger than 2 GiB.

**GUEST-30.** No artifact can be named after a fixed path: a `POST` to
`/heartbeat`, `/exit`, `/ca.pem`, `/ca.crl`, `/build-script` or `/bootstrap`
is that path's request, not an upload (GUEST-31). The build environment
MUST NOT upload an artifact under one of those names.

**GUEST-31.** The build environment MUST use `POST` for `/exit` and `GET`
for the other fixed paths. The relay MUST serve each fixed path for that
method, and MAY serve it whatever the method; the Go relay does (Known
divergences, D9).

**GUEST-32.** To any other request for `artifacts`, a request that is not a
`POST` to a path that is not fixed, the relay MUST answer `404`; the Go
relay's body is `not found` and a line feed. There is no
`http://artifacts/health` (Known divergences, D12): the relay's health is on
the control plane (GUEST-36).

### The reserved host `cwd`

The build context is the set of files the collector serves the build
(`collector-inputs`). The build environment reads it as `http://cwd/<path>`;
the reference executor's `fetch` reads a listing, then each file in it.

**GUEST-33.** For a `GET` for `cwd`, the relay MUST take the context path
from the request's path without its leading `/`, and without a trailing
`/`. When that path is not empty and breaks the rule of GUEST-28 as it
stands for a context path, under which a segment may also start with `.`,
`-` or `_` (but is still not `.` or `..`), the relay MUST answer `403` with the body `forbidden` and a line feed, and
fetch nothing. The build environment MUST send only paths that keep the
rule.

**GUEST-34.** Otherwise the relay MUST fetch the path from its collector
(`GET /v1/context/<path>`, `collector-inputs`, with each segment escaped and
a trailing `/` kept) and answer by what the collector gives:

- a file: `200` with `Content-Type: application/octet-stream` and the
  file's bytes unchanged, recorded (GUEST-49);
- a listing, which the collector gives for the context's root, for a
  directory and for a path with a trailing `/`: `200` with
  `Content-Type: text/plain` and the listing's bytes unchanged, not
  recorded;
- anything but `200` (the path does not exist): `404`, with the body
  `not found: <path>` and a line feed in the Go relay.

The Go relay answers `404` as well when the collector cannot be reached;
this version does not define that reply. The listing's form, and how the
collector tells a listing from a file, are `collector-inputs`'.

### The control plane

**GUEST-35.** The relay MUST serve the control plane as HTTP/1.1 on TCP
port 8300 of the relay's address (on a frame link, port 8300 of any
address, GUEST-6). The control plane does not route by `Host`.

**GUEST-36.** To `GET /health` the relay MUST answer `200` with the body
`ok` (no line feed). The build environment uses it to learn that the relay
is serving (GUEST-52).

**GUEST-37.** To `GET /ca.pem` the relay MUST answer as to
`http://artifacts/ca.pem` (GUEST-23): `200` with
`Content-Type: application/x-pem-file` and the same bytes, not recorded.

**GUEST-38.** To `POST /v1/output` the relay MUST forward the request's
body, as it receives it and whatever its `Content-Type`, as one
`POST /v1/output` to its collector (`collector-outputs`), and answer `200`
with an empty body once the collector has answered `200`. The body is the
build's console output, in order; it is an output and not recorded. The
relay MUST forward at most 256 MiB (268435456 bytes) of output in all for
one build, and MUST answer `413` with the body `output limit exceeded` and
a line feed to a request that arrives once it has forwarded that much. The
request that crosses the limit MUST be cut short at it, and SHOULD be
answered `413`; it MAY be answered `200`, as the Go relay does (Known
divergences, D11). When the collector does not take the output the relay
MUST answer `500` with a body that says why.

**GUEST-39.** To `POST /v1/complete?code=<n>` the relay MUST complete the
build as for `http://artifacts/exit` (GUEST-21, GUEST-22), and answer `200`
with an empty body.

**GUEST-40.** To `/v1/output` or `/v1/complete` with any method but `POST`,
the relay MUST answer `405` with the body `POST only` and a line feed, and
do nothing else. To any other clean path, one with no empty segment and no
`.` or `..` segment, the relay MUST answer `404`. The Go relay answers
`/health` and `/ca.pem` whatever the method.

This version does not define the reply to a path that is not clean, or to
an HTTP/1.1 request without `Host`. The Go relay's control plane is Go's
`net/http` server: it redirects a path that is not clean to its clean form
with `307` (`/./health` to `/health`, `/v1//output` to `/v1/output`), and
answers an HTTP/1.1 request without `Host` with `400`.

### Every other host: the proxy and interception

**GUEST-41.** On TCP port 80 (and on a frame link every port but 443 and
8300, GUEST-6), the relay MUST serve HTTP/1.0 and HTTP/1.1 requests in
origin form and in absolute form, and MUST proxy each request for a host
that is not reserved (GUEST-17) to that host: over HTTP, to the host and
port the request names (its absolute URL, or else its `Host`), port 80 when
it names none. It MUST record the exchange (GUEST-49).

This version defines only targets in origin form and `http:` targets in
absolute form. The Go relay proxies an `https:` target in absolute form
over HTTPS (to port 443 when it names none), and sends a `CONNECT` upstream
as an ordinary request without opening a tunnel.

**GUEST-42.** On TCP port 443 (and on a frame link port 443 of any address),
the relay MUST terminate TLS with a certificate for the server name the
client sent (SNI), and then serve the HTTP/1.x requests inside the
connection as on port 80, routing them by their target host (GUEST-17). The
certificate MUST:

- be signed by the relay's certificate authority (GUEST-48), and be sent
  with the authority's certificate after it;
- name the server name as its one DNS subject alternative name, or, when
  the name is an IP address, as its one IP address subject alternative name;
- allow server authentication (extended key usage `serverAuth`);
- name `http://artifacts/ca.crl` as its CRL distribution point (GUEST-24);
- be valid, with the authority's certificate, whenever the relay presents
  it within 24 hours of its claim.

The Go relay makes one certificate for each server name, the first time the
name is asked for, and keeps it for its life: an ECDSA P-256 key, valid from
one hour before it is made until 24 hours after. Its authority's
certificate expires 24 hours after the claim (GUEST-48), and the relay
makes no new one, so from then on it presents a chain that has expired,
and from 24 hours after a leaf was made, a leaf that has. What a relay
presents more than 24 hours after its claim is not defined by this
version.
How a relay answers a TLS client that sends no server name is not defined by
this version.

**GUEST-43.** The relay MUST proxy a request it receives inside TLS to the
server name the client sent (SNI), over HTTPS on port 443, with the
request's `Host` unchanged, and MUST verify the upstream's certificate
against the roots the claim gave it (`relay-claim`: `upstream_ca_certs` and
`upstream_system_ca`). It MUST record the exchange (GUEST-49).

**GUEST-44.** The relay MUST send the build environment the response as the
upstream sent it: its status, its header fields and its body, unchanged
(RELAY-02 in buildwarden/buildwarden). Unchanged means the same fields with
the same values; the case of a field's name and the order of the fields are
not significant, and the relay MAY add `Connection: close` (GUEST-47). It
MUST NOT ask the upstream for an encoding the build environment did not ask
for, and MUST NOT decode the body. Where it changes anything the build
environment receives, it records what it sent (GUEST-49).

The Go relay writes each field's name in Go's canonical form (`x-lower`
as `X-Lower`) and the fields in its own order, the same in what it sends
and in what it records. It adds `Connection: close` when it will close the
connection (GUEST-47) and when the response has no length; it records the
response's header fields before it adds that field, so its record of them
lacks it, and for its own `502` (GUEST-46) the record has
`Content-Length: 0` where the reply sent has no length.

**GUEST-45.** The relay MUST resolve an upstream's name through its
upstream resolvers only, in their list order, as it forwards the build
environment's queries (GUEST-15); it asks for A and AAAA records and tries
IPv4 addresses first. An IP address in place of a name is used as it is.

**GUEST-46.** The relay MUST answer `502` with `Content-Type: text/plain` and
the body `upstream unreachable` and a line feed when it cannot reach the
upstream (its name does not resolve, or no address accepts the connection,
or the exchange fails), and when it refuses to connect to it. A relay with a
build link (vm mode, and host mode) MUST refuse every address inside the
build link, its own included (`relay-claim`). A host-mode relay, on a frame
link, MUST refuse besides every loopback, unspecified, private (RFC 1918, RFC 4193),
link-local unicast and link-local multicast address, and the cloud metadata
addresses 169.254.169.254 and 100.100.100.200. The relay MUST refuse a name
when any of the addresses it resolves to is refused. A container-mode relay
refuses no address itself: what its container may reach is the driver's.
The `502` is recorded as the exchange's response (GUEST-49).

How the `502` is framed is not defined by this version. The Go relay sends
it with `Connection: close` and no length, so that its body ends only when
the connection closes; and it does not close the connection (GUEST-47).

**GUEST-47.** The relay MUST keep a connection open for the next request
after it has answered an HTTP/1.1 request, unless the request or the
response says `Connection: close`, and after an HTTP/1.0 request only when
it says `Connection: keep-alive`, spelled so, in lower case and as the
field's whole value; how a relay treats another spelling is not defined by
this version, and the Go relay closes the connection. The Go relay does not
send `Connection: keep-alive` back to an HTTP/1.0 client, and answers the
reserved hosts' requests as `HTTP/1.1`.

What a relay does after it has sent a response that says
`Connection: close`, or whose body ends at the connection's close, is not
defined by this version. The Go relay closes the connection when the
request said `Connection: close`, or was HTTP/1.0 without
`Connection: keep-alive`. Otherwise it keeps the connection open even when
the response says `Connection: close`: its own `502` (GUEST-46), and an
upstream's response that says `Connection: close` or has no length (an
HTTP/1.0 response that ends at the close, for one). A client that reads
such a response to the close then waits until it gives up. A client of a
request that may be proxied therefore sends `Connection: close` on it, and
the suites do so.

### The certificate authority

**GUEST-48.** The relay MUST create its certificate authority once, at its
claim, for the build alone, and MUST NOT use it for anything but the
certificates of GUEST-42 and the CRL of GUEST-24. Its certificate MUST be a
CA certificate (basic constraints with CA true and a path length of 0) that
allows certificate signing and CRL signing, and MUST be valid when the
relay answers the claim. The Go relay's authority is an RSA 2048-bit key
named `BuildWarden Ephemeral CA`, valid from one hour before the claim until
24 hours after.

### What the relay records

**GUEST-49.** The relay MUST record in its ledger, as
[`specs/build-ledger/v1.md`](https://github.com/buildwarden/buildwarden/tree/main/specs/build-ledger/v1.md)
in buildwarden/buildwarden defines the records:

- each exchange it proxies (GUEST-41, GUEST-43): the request's opening,
  its header fields and its body, and the response's header fields and its
  body, as sent to the build environment, a `502` of GUEST-46 included;
- the bytes it serves at `/build-script` and `/bootstrap`, and each file it
  serves from `cwd`, as the body of a `GET`'s response with status 200;
- each artifact it stores (GUEST-27).

For its own `502` the Go relay's record of the response's header fields
differs from what it sent: the record has `Content-Length: 0` and no
`Connection` field, and the reply has no length and `Connection: close`
(GUEST-44, GUEST-46).

**GUEST-50.** The relay MUST NOT record what it serves at `/ca.pem`, on
either server, or at `/ca.crl`: they are the relay's own trust material and
not inputs that can change what a build produces.

The Go relay records nothing else of this API: not the heartbeat, the
completion, a listing of `cwd`, a refusal of GUEST-28, GUEST-29 or GUEST-33,
the control plane's requests, DHCP, ARP or DNS. This version neither
requires nor forbids a record of them.

## Ordering

**GUEST-51.** The relay MUST serve none of this document's services on the
build link before it has been claimed (`relay-claim`). Where it serves the address lease it MUST
serve it before it answers the claim. A relay on a frame link MUST have
every service of this document ready before it answers the claim. A relay on
a kernel interface MAY still be binding its ports when it answers the
claim (Known divergences, D19).

**GUEST-52.** The build environment MUST NOT send a request to the reserved
hosts, or through the proxy, before `GET /health` on the control plane has
answered `200`: it SHOULD retry that request until it does. The reference
executor asks every 500 ms for at most 60 s (`executor-initialize`).

**GUEST-53.** The build environment MUST send all of its console output
(GUEST-38), and have its replies, before it completes the build.

**GUEST-54.** The build environment MUST complete the build once, with
`POST http://artifacts/exit?code=<n>` (GUEST-21) or
`POST /v1/complete?code=<n>` on the control plane (GUEST-39); the reference
executor uses `/exit`. The reference executor does not complete the build
when it fails before the build script runs (`executor-initialize`, Known
divergences, D13).

**GUEST-55.** Completion is terminal for this API. After it the build
environment MUST send nothing more, and the relay MUST NOT record anything
more. Its replies to requests after completion are not defined by this
version. The Go relay keeps its listeners, and still answers `/heartbeat`,
`/ca.pem`, `/ca.crl`, listings of `cwd` and a repeated `/exit`; a request it
would record ends its process (Known divergences, D18).

## Errors

The relay's replies to a request it does not serve as asked:

| Where | Status | Body | When |
|---|---|---|---|
| `artifacts` | `400` | `invalid artifact name` | An artifact's name breaks the rule (GUEST-28) |
| `artifacts` | `413` | `artifact size limit exceeded` | An artifact over 2 GiB (GUEST-29; N33) |
| `artifacts` | `500` | `storage error` (Go relay) | The collector did not store the artifact (GUEST-29) |
| `artifacts` | `404` | `build script unavailable`, `no bootstrap config` (Go relay) | The collector has no build script or no bootstrap config (GUEST-25, GUEST-26) |
| `artifacts` | `404` | `not found` (Go relay) | No such path (GUEST-32) |
| `cwd` | `403` | `forbidden` | A context path that breaks the rule (GUEST-33) |
| `cwd` | `404` | `not found: <path>` (Go relay) | No such context path (GUEST-34) |
| Control plane | `405` | `POST only` | `/v1/output` or `/v1/complete` with another method (GUEST-40) |
| Control plane | `413` | `output limit exceeded` | Output after 256 MiB (GUEST-38) |
| Control plane | `500` | Why | The collector did not take the output (GUEST-38) |
| Control plane | `404` | | No such path (GUEST-40) |
| Proxy | `502` | `upstream unreachable` | An upstream the relay cannot reach or refuses (GUEST-46) |
| DNS | SERVFAIL | | No upstream resolver answered (GUEST-16) |

**GUEST-56.** The relay MUST send each refusal of this document as
`Content-Type: text/plain`, with or without parameters, and a body of at
most one line.

A refusal changes nothing but what the table says: the build environment
may go on.

## Limits

- An artifact is at most 2 GiB (GUEST-29), and its name at most 255 bytes
  (GUEST-28); a context path is at most 255 bytes (GUEST-33).
- The build's console output is at most 256 MiB in all (GUEST-38).
- An upstream resolver is given 5 s before the next is asked (GUEST-15).
- The heartbeat's 2 s and 5 s (GUEST-20).

Other numbers are the Go relay's own and not this document's: it holds a
file of the build context, the build script and the bootstrap config in
memory, reads at most 2 GiB of each from the collector, and waits up to
5 minutes for the collector to give one; on a frame link it queues at most
16 connections for each service that it has not yet accepted, and closes
any more; and its frames are at most 1500 bytes of IP.

## Versioning

The API carries no version of its own today beyond `/v1/` on two of the
control plane's paths, `/v1/output` and `/v1/complete`, which name version 1
and so this document: `v1.md` is version 1. While this specification's
releases are `v0.x.y`, the document is edited in place and may still change
incompatibly; from `relay-guest-api/v1.0.0` on, version 1 changes only
compatibly, and an incompatible change is a new document `v2.md`.

The umbrella design's proposed BOOT-02 in buildwarden/buildwarden has the
executor and the relay "agree through the relay guest API's version". That
version does not exist yet: it is added with the truststore endpoints, by
the item that changes the executor's `initialize` (phase S2 of the
componentization program), and this document is then given a way for the
build environment to ask for it.

## Conformance

A relay conforms to this version when it meets every requirement of the
relay: GUEST-1; GUEST-2 on a kernel interface, or GUEST-3 to GUEST-7 on a
frame link; GUEST-8 to GUEST-11 where it serves the address lease;
GUEST-12 to GUEST-17; GUEST-19 to GUEST-51 for their relay's part; GUEST-55
for its part; and GUEST-56.

A build environment conforms to this version when it meets every
requirement of the build environment: GUEST-18, GUEST-20 and GUEST-22 for
their part, GUEST-28, GUEST-29 and GUEST-30 for theirs, GUEST-31 for its
part, GUEST-33 for its part, GUEST-52 to GUEST-54, and GUEST-55 for its
part. The executor's side of this API is tested by no suite of this
version: its requirements are on the directory's list of requirements no
case checks.

## Known divergences

Places where the reference implementation differs from a rule or a comment
of its own repository, or from the rest of this protocol. Each is what the
code does, and the requirements above allow it where they name it. The
numbers D9 to D19 are those of the design that wrote this document,
`docs/design/seam-specs.md` in buildwarden/buildwarden, under "Divergences
found", a table that holds D1 to D19 and N1 to N33; the N numbers are
shared by the six documents. The line numbers are those of buildwarden/buildwarden at
`623131a`, where the files they name are as they were at `3cb0b2b`.

### D9: the fixed paths of `artifacts` ignore the method

The Go relay serves `/heartbeat`, `/exit`, `/ca.pem`, `/ca.crl`,
`/build-script` and `/bootstrap` on `artifacts` whatever the request's
method. So a `GET /exit?code=3` completes the build with exit code 3, as
the reference executor's `POST` does (GUEST-31).

### D10: a `cwd` request that is not a `GET` is proxied

The Go relay serves `cwd` only for `GET`. Any other method for `cwd` is
proxied as if `cwd` were an upstream host, which `cwd`, a reserved name,
is not: it resolves through the relay's upstream resolvers, and when it does
not resolve the reply is `502 upstream unreachable` (GUEST-17, GUEST-46).

### D11: the output limit is reported one request late

The `POST /v1/output` that crosses the 256 MiB limit is cut short at the
limit and still answered `200`; only the next request is answered `413`
(GUEST-38). A limit is otherwise reported when it is hit.

### D12: there is no `http://artifacts/health`

`http://artifacts/health` is not a path of the Go relay, and is answered
`404` (GUEST-32). The relay's health is `GET /health` on the control plane
(GUEST-36). The reference executor, started with neither `--gateway` nor
`WARDEN_GATEWAY`, polls `http://artifacts/health` instead, and gives up
after 60 s; every driver passes `--gateway`. The executor's side is in
`executor-initialize`.

### D15: no DNS over TCP on a frame link

In vm and container mode the Go relay serves DNS over UDP and TCP. In host
mode, on a frame link, it serves DNS over UDP only, and a TCP connection to
port 53 reaches the HTTP proxy like any port that is not 443 or 8300
(GUEST-6, GUEST-12).

### D18: a recorded request after completion ends the relay

Once the build has completed (GUEST-21, GUEST-39), the Go relay's ledger has
ended. A request after it that the relay would record (a proxied request,
`/build-script`, `/bootstrap`, a file of `cwd`, an artifact upload) sends
to the ledger's closed channel in the goroutine that serves the connection,
which nothing recovers, and so ends the relay's process. Requests it does
not record are still answered, a repeated `/exit` among them. Completion
had no stated after-state before this document; GUEST-55 leaves the replies
undefined and requires only that nothing more is recorded, which the Go
relay meets by ending.

Seen against the Go relay built from buildwarden/buildwarden at `3cb0b2b`,
in container mode in a network namespace of its own, claimed by
`cmd/collector` from the same commit: `GET /exit?code=3` on `artifacts` was
answered `200 ok`, and the collector reported the build's exit code 3 and
ended. After it, `/heartbeat`, `/ca.pem`, `/ca.crl` and a repeated
`POST /exit` were still answered `200`. Then a `GET` with `Host:
example.invalid` on port 80 got no reply: the relay ended with exit status
2 and `panic: send on closed channel`, raised from the ledger's `Open`
called by the proxy's request handler, in a goroutine started by the
port-80 listener.

### D19: vm and container mode answer the claim before their ports are bound

In vm and container mode the Go relay answers the claim, and sends the
collector `ready`, once it has started the goroutines that bind and serve
its ports, not once the ports are bound (GUEST-51). A port that then fails
to bind ends the relay after its `200`, and a failed bind of UDP port 53 is
not reported at all. In host mode the relay's services are ready before it
answers. A build environment that waits for `/health` (GUEST-52) is not
affected by a slow bind.

### N17: a connection is kept open after a response that says close

`ServeHTTPConn` and `ServeTLSConn` decide whether to keep a connection with
`shouldKeepAlive` (`relay/proxy.go:283-354`, `:381-393`), which reads the
request and the response's `Connection` header field, and neither the
response's `Close` nor its framing; `Response.Write` then sends a body of
no known length with `Connection: close`, to end at the close. So for the
relay's `502` (`relay/proxy.go:362-372`) and for an upstream's response
that says `Connection: close` or has no length, an HTTP/1.1 request
without `Connection: close` keeps the connection open while the response
is sent as ending at its close (GUEST-46, GUEST-47). A client that reads that body to the close waits until it gives
up. This differs from RFC 9112, under which a response framed by the close
is followed by the close, and from the relay as a transparent proxy.
Seen against the Go relay at `3cb0b2b`: the `502` arrived with
`Connection: close` and no length, and the client then timed out reading;
with `Connection: close` in the request it ended normally; an upstream's
`HTTP/1.0 200` with no length hung the same way.

### N18: a frame link answers ICMP

On a frame link the relay's network stack is gVisor's
(`cmd/relay/ingress_fd.go:93-98`), which answers an ICMP echo request to the
relay's address, and answers UDP to a port the relay does not serve, at its
address or at any other, with ICMP port unreachable whose source is the
address the datagram was sent to: an address the relay does not hold
(GUEST-7). This differs from the relay as the build's one network path that
answers only for the services it states, and the second answer speaks for
hosts the build cannot reach. Seen against the Go relay at `3cb0b2b`: an
echo to 10.100.0.1 got type 0 and one to 8.8.8.8 nothing; UDP to port 9999
at 10.100.0.1 got type 3, code 3, from 10.100.0.1; UDP to 8.8.8.8 on port
9999 or 53 got type 3, code 3, from 8.8.8.8.

### N19: the authority and its certificates expire after 24 hours

The authority's certificate and each leaf are valid until 24 hours after
they are made (`relay/relay.go:338`, `relay/proxy.go:246`), and the leaves
are kept for the relay's life with no check of their expiry
(`relay/proxy.go:234-277`). A build that runs longer than 24 hours is then
presented a chain that has expired, and its TLS requests fail (GUEST-42,
GUEST-48). Nothing in the design or the code states a limit on a build's
length. Seen against the Go relay at `3cb0b2b`: the leaf and the
authority were each valid from an hour before they were made until 24
hours after, and a second request for a name was given the cached leaf.

### N20: what is recorded of a response is not what was sent

The relay records a response's header fields with `httputil.DumpResponse`
(`relay/relay.go:589-610`) before it adds `Connection: close`, and writes
each field's name in Go's canonical form and the fields in its own order
(GUEST-44). For its own `502` the record has `Content-Length: 0` and no
`Connection` field, where the reply sent has no length and
`Connection: close` (GUEST-49). This differs from RELAY-02 in
buildwarden/buildwarden, under which what the build receives is recorded
byte for byte. Seen against the Go relay at `3cb0b2b`: `x-lower` arrived
and was recorded as `X-Lower`, the fields were reordered, and the record of
a `502` differed from the reply as above.

### N21: an exit code that cannot be read is success

The relay reads `code` with `fmt.Sscanf("%d")` and ignores its error
(`relay/relay.go:505-508`, `relay/controlplane.go:56-60`), so a value it
cannot read, or one beyond a signed 64-bit integer, is the exit code 0,
which is success, and a value with trailing text is its leading integer
(GUEST-22). This differs from GLOBAL-10 in buildwarden/buildwarden: a
provided value that cannot be used is accepted, here as a success. Seen
against the Go relay at `3cb0b2b`: `99999999999999999999` was 0, `7x` was
7 and `+5` was 5.

### N22: `keep-alive` is matched in lower case only

For an HTTP/1.0 request the relay keeps the connection only when its
`Connection` field is exactly `keep-alive` (`relay/proxy.go:391`), so
`Keep-Alive`, or the token in a list, closes it (GUEST-47). This differs
from RFC 9110, under which connection options are case-insensitive and the
field is a list. Seen against the Go relay at `3cb0b2b`.

### N23: the reserved names are matched exactly

The relay serves `artifacts` and `cwd` only when the name is exactly so
spelt: in DNS, the query's name without its root against a map
(`relay/dns.go:59-62`), and in HTTP, the `Host` before its first `:`
(`relay/relay.go:527-535`). `Host: ARTIFACTS` and `Host: artifacts.` are
therefore proxied as upstream hosts, and a query for `ARTIFACTS` is
forwarded to the upstream resolvers (GUEST-18 leaves other spellings
undefined). This differs from RFC 4343 and RFC 9110, under which host names
are case-insensitive, and from the reserved names as the relay's own: a
build that spells one otherwise leaks the request upstream. Seen against
the Go relay at `3cb0b2b`: both `Host` spellings got `502` from the proxy,
and the query was forwarded.

### N24: a collector's failure is served as "none"

`handleBuildScript`, `handleBootstrap` and `handleContextGet` answer `404`
when the collector's reply is not `200` or the request to it fails
(`relay/relay.go:719-738`, `:751-752`), so the build cannot tell a
collector that has no bootstrap config from one that failed (the paragraph
after GUEST-26). The executor reads a `404` from `/bootstrap` as the empty
config, whose trust mode is `append` (`bootstrap-config`), so a collector
that fails turns a producer's `exclusive` into `append`: the build trusts
the system's roots as well, where it was to trust the relay's alone. This
differs from the function's own comment ("A collector without one gives
404", `relay/relay.go:728-731`), and from GLOBAL-10 in
buildwarden/buildwarden, under which the default is not tried when a
provided value fails. Run for `bootstrap` by `bootstrap-config`'s cases
against the Go relay in host, vm and container mode: a collector that
answered `GET /v1/bootstrap` `500` while it held a config, and a request to
the collector that failed, each gave the build `404`; for `cwd`, this
suite's case has a path the collector answers `500` served as `404`. The
executor's reading of that `404` as `append` is read from the code.

### N25: a refused artifact leaves an open record

`handleArtifactPost` opens the exchange's record and writes its request
header checkpoint (`relay/relay.go:650-666`) before it streams the body to
the collector, and on a `413` or a `500` (`relay/relay.go:672-680`) returns
without closing that record; the bytes already streamed have reached the
collector's `PUT /v1/artifacts/<name>` too (GUEST-29). The ledger then has
an open that no record closes, which `specs/build-ledger/v1.md` in
buildwarden/buildwarden does not expect of a complete exchange. Read from
the code; not run.

### N33: an artifact of 2 GiB and one byte is stored

`handleArtifactPost` reads the body through a `limitedReader` that allows
2 GiB and one byte (`relay/relay.go:670`), and that reader fails only on a
read made once nothing is left (`relay/collector_client.go:290-301`).
The body `net/http` reads for `http.ReadRequest` returns its last bytes
together with the end of a body sent with `Content-Length`, so for one of
exactly 2 GiB and one byte no such read is made: the artifact is streamed
to the collector, recorded and answered `200`. A body of 2 GiB and two
bytes or more is answered `413` (GUEST-29). This differs from the limit the
relay's own `maxArtifactBytes` (`relay/relay.go:161`) and its `413` state,
2 GiB. Seen against the Go relay at `8c41eaa`, whose `relay/` is as it is at
`623131a`, in host, vm and container mode: a body of 2147483649 bytes was
answered `artifact stored: big.bin (2147483649 bytes)` and recorded, and
one of 2147483650 bytes was answered `413`.
