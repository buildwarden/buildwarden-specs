# collector-inputs, version 1

The inputs and signals a collector serves a relay.

| | |
|---|---|
| Seam | 2, the collector protocol: the inputs and signals |
| Requirement identifiers | `COLLIN-<n>` |
| Roles | collector, relay |
| Concept | [The collector](https://buildwarden.github.io/buildwarden/concepts/architecture.html#collector-collector-library-cmdcollector-binary) in the BuildWarden book |
| Reference implementation | The disk collector, `cmd/collector` with `collector/`; the relay side in `relay/`, in [buildwarden/buildwarden](https://github.com/buildwarden/buildwarden) |
| Status | Not yet released. While its release is `v0.x.y` this document may still change incompatibly; see Versioning |

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY" and "OPTIONAL" in this
document are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174)
when, and only when, they appear in all capitals. A requirement is a
paragraph or list item that starts with its identifier in bold.

## Scope and roles

This document specifies what a collector serves a relay during a build: the
build's inputs, which the relay fetches when the build asks for them (the
build script, the bootstrap config and the files of the build context), and
the signals the relay sends it (`ready`, `heartbeat` and `complete`), with
the two endpoints that report on the session and that no relay calls,
`/v1/status` and `/healthz`.

The outputs a collector stores for the same relay (the artifacts, the
captures, the ledger, the environment payload and the console) are the other
specification of this seam, `collector-outputs`. What the build itself sees
of the inputs, at `http://artifacts/build-script`, `http://artifacts/bootstrap`
and `http://cwd/<path>`, is the relay's guest API, `relay-guest-api`. The
bootstrap config's own format is `bootstrap-config`.

The machine-readable description of these endpoints is
[`v1.openapi.json`](v1.openapi.json), beside this document, with the JSON
Schemas of its two JSON bodies, [`v1.complete.schema.json`](v1.complete.schema.json)
and [`v1.status.schema.json`](v1.status.schema.json). Where they and a
requirement here differ, the requirement stands.

### The session

Seam 2 is one seam, the collector protocol, written as two specifications:
`collector-outputs`, the outputs a collector stores, and `collector-inputs`,
the inputs and signals it serves. Each has its own requirement prefix, its
own suite and its own releases, so a collector may implement one of them and
claim it. Nothing on the wire tells them apart: the claim names one
collector, and a relay sends the requests of both to it. Five subsections are
stated alike in the two documents, but for the prefix of their identifiers,
and change together: this one, *HTTP, and where the collector is*,
*Authentication*, *Names in paths*, and *D8* under Known divergences.

The roles are the same in both. The *collector* serves the protocol. The
*relay* is the only client of it: no other party sends a request that this
protocol specifies. Who starts a collector, and where it runs, is outside the
protocol.

**COLLIN-1.** The protocol's unit is the build *session*: the requests of one
build, which a collector tells apart by the collector token they carry (see
Authentication). A collector MUST apply every rule of this document to each
session on its own. A collector that is given no token has exactly one
session.

**COLLIN-2.** A session's completion, its first `POST /v1/complete` (which
`collector-inputs` specifies), is terminal. Once a collector has received it,
the collector owes the relay nothing more for that session, and it MAY close
the connection the session's requests arrive on at once, before it replies to
any of them.

How many sessions one instance of a collector serves is the collector's own.
A collector declares it in its target file.
The reference disk collector, `cmd/collector`, serves exactly one session and
then exits, with status 0 when the completion's `exit_code` is 0 and 1
otherwise. A collector that serves several sessions, and any side of a
collector that faces its own clients (opening a session, supplying inputs,
watching the console and the status, fetching the outputs), is outside this
version of the protocol.

## Transport

<!-- collector-common: begin -->
### HTTP, and where the collector is

The relay reaches the collector at the base URL the claim names, its
`collector_url` (`relay-claim`, Messages and fields). The value
`http://collector.tunnel` selects the tunnel the claimant opened on the
relay's claim endpoint, which carries HTTP/2 with prior knowledge and no TLS
with the relay as the client (`relay-claim`, Transport). Any other value is a
base URL that the relay dials itself, with HTTP as its scheme allows.

**COLLIN-3.** A collector MUST serve each endpoint of this document at the
path this document gives it, appended to the base URL the claim names, over
HTTP: over the tunnel when the claim selects it, and otherwise at that base
URL.

**COLLIN-4.** The relay MUST send every request of a session to the base URL
its claim named, with the path appended to it once any trailing `/` of the
base URL is removed.

### Authentication

**COLLIN-5.** Where a session has a token, a collector MUST require it on
every request to an endpoint under `/v1/` that this protocol specifies, except
`GET /v1/status`. It MUST answer a request that carries no token, or another
one, with 401 and the body `unauthorized` followed by a line feed, whatever
the request's method, name or body, its path being one that a relay may send
(COLLIN-12).

**COLLIN-6.** A collector MUST NOT require a token for `GET /healthz` or for
`GET /v1/status`.

**COLLIN-7.** A collector MUST accept the token in the `Authorization` header
in the form `Bearer <token>`, with one space after `Bearer`.

**COLLIN-8.** A collector that has no token MUST NOT refuse a request for what
its `Authorization` header holds or lacks.

**COLLIN-9.** When the claim's `collector_token` is not empty, the relay MUST
send `Authorization: Bearer <token>` on every request of the session. When it
is empty, the relay MUST send no `Authorization` header.

**COLLIN-10.** A collector SHOULD compare a request's token with the
session's in a time that does not depend on how much of it matches.

## Messages and fields

<!-- collector-common: begin -->
### Names in paths

Some endpoints carry a name in their path: an artifact's name and a capture's
in `collector-outputs`, a context path in `collector-inputs`. A name is the
part of the path after the endpoint's prefix, as the collector reads it once
the path is percent-decoded.

**COLLIN-11.** A name is *safe* when it is a relative slash path of 1 to 255
bytes, none of whose segments is empty, `.` or `..`, and whose bytes are all
in `[A-Za-z0-9._-]` or are the `/` between segments, and when it also keeps
the rule its own document adds for that kind of name. A collector MUST NOT
store, serve or list anything under a name that is not safe by its own
document's rule for it.

**COLLIN-12.** The relay MUST percent-encode each segment of a name it
carries in a path, and MUST NOT send a path in which `//`, `/./` or `/../`
occurs or that ends in `/.` or `/..`. What a collector answers to such a path
is not specified by this version, whether or not the request carries the
token. The disk collector answers it, before it looks at the token, with 307
and a `Location` that is the path with those segments resolved.
<!-- collector-common: end -->

### The endpoints

| Endpoint | Reply |
|---|---|
| `GET /v1/build-script` | 200, `application/octet-stream`; 404 when the build has none |
| `GET /v1/bootstrap` | 200, `application/json`, the bootstrap config; 404 when the build has none |
| `GET /v1/context/<path>` | A file, or a listing of the files beneath a directory; 403 for a path that is not safe; 404 for one that is not there |
| `POST /v1/ready` | 200. The relay is up |
| `POST /v1/heartbeat` | 200. The build is alive |
| `POST /v1/complete` | 200. The build's result; 400 for a body that is not one |
| `GET /v1/status` | 200, `application/json`: the result, or that the build is running. No relay calls it |
| `GET /healthz` | 200, `ok`. No relay calls it |

### The inputs

**COLLIN-13.** A collector MUST answer `GET /v1/build-script` with 200, the
`Content-Type` `application/octet-stream` and the bytes of the session's
build script, or with 404 when the session has none.

**COLLIN-14.** A collector MUST answer `GET /v1/bootstrap` with 200, the
`Content-Type` `application/json` and the session's bootstrap config, the
document `bootstrap-config` specifies, byte for byte; or with 404 when the
session has none. A relay and an executor read the 404 as the empty config
(`bootstrap-config`).

A context path is the part of the path after `/v1/context/`. It names a file
or a directory of the session's build context, relative to the context's
root. The empty path, `GET /v1/context/`, names the root.

**COLLIN-15.** A context path, less one trailing `/`, is a safe name
(COLLIN-11) each of whose segments also ends with a letter or a digit; a
segment may start with `.`, `-` or `_`, so that a directory such as
`.warden/` can be reached. When the session has a build context, a collector
MUST answer 403 to a context path that is not empty and is not such a name,
and serve nothing for it.

**COLLIN-16.** When a context path names a file and does not end in `/`, a
collector MUST answer 200 with the header `Warden-Context: file`, the
`Content-Type` `application/octet-stream` and the file's bytes.

**COLLIN-17.** When a context path is empty, names a directory, or names a
directory and ends in `/`, a collector MUST answer 200 with the header
`Warden-Context: list`, the `Content-Type` `text/plain` and a listing: the
paths of the files beneath that directory, at any depth, relative to the
context's root, each a safe context path (COLLIN-15), sorted by their bytes,
each followed by a line feed. A listing names files only, and an empty
listing is an empty body.

**COLLIN-18.** A collector MUST answer 404 to a context path that names
nothing in the context, to a context path that names a file and ends in `/`,
and to every context path when the session has no build context.

**COLLIN-19.** A collector MUST NOT serve or list a symbolic link that leads
out of the build context, or anything reached through one; a context path
that names one is answered 404. A symbolic link that leads to a directory
inside the context is not listed. What a collector answers to a context path
that names such a link, or leads through one, is not specified by this
version; the disk collector serves the directory or the file it leads to, and
lists the directory's files under the link's path.

**COLLIN-20.** A collector MUST answer 405 to a method other than `GET` on
`/v1/build-script`, `/v1/bootstrap` and `/v1/context/`.

### The signals

**COLLIN-21.** A collector MUST answer `POST /v1/ready` with 200. The request
has no body. It means that the relay is up and serving the build.

**COLLIN-22.** A collector MUST answer `POST /v1/heartbeat` with 200. The
request has no body. It means that the build has shown activity in the last
few seconds (COLLIN-30).

**COLLIN-23.** A collector MUST answer `POST /v1/complete` with 200 when its
body is a JSON object in which each of the three members below appears once
and is of its type, with `exit_code` written with no fraction and no exponent
and in the range of a signed 64-bit integer, and in which no other member's
name is one of the three in another case of its letters; it MUST then ignore
every other member. It MUST answer 400 when the body is not JSON, when it is
a JSON array, string, number or boolean, and when one of the three members has
a value that is of another type and is not `null`. It MAY answer 400 to an
`exit_code` with a fraction or an exponent, or outside that range.

| Member | Type | Meaning |
|---|---|---|
| `exit_code` | integer | The build's exit code: 0 is success |
| `message` | string | Text for a person about the build's end; may be empty |
| `error` | string | Text for a person about a failure of the build's run; may be empty |

```json v1.complete.schema.json
{"exit_code": 0, "message": "", "error": ""}
```

What a collector answers to, and records from, a body that is `null`, that
lacks one of the three members or has one whose value is `null`, that has more
after the object, or that names a member twice or in another case of its
letters, is not specified by this version. The disk collector answers each
with 200: it reads a missing or `null` member as 0 or the empty string,
ignores what follows the object, and matches the three names without regard
to case, keeping the last of the members it matches to one name.

**COLLIN-24.** The first completion a session receives is the build's
result. A collector MUST answer a later one as COLLIN-23 has it and MUST NOT
let it change the result.

**COLLIN-25.** A collector MUST answer a method other than `POST` on
`/v1/ready`, `/v1/heartbeat` and `/v1/complete` with 405.

### The session's status

**COLLIN-26.** A collector that serves one session MUST answer
`GET /v1/status` with 200 and the `Content-Type` `application/json`: before
the session's completion, the object `{"state":"running"}`; after it, the
first completion's three members and `received_at`, the time the collector
received it, as an RFC 3339 date and time. It MUST answer 405 to another
method on `/v1/status`.

```json v1.status.schema.json
{"state": "running"}
```

```json v1.status.schema.json
{"exit_code": 3, "message": "", "error": "", "received_at": "2026-11-16T10:04:05.123456789Z"}
```

**COLLIN-27.** A collector MUST answer `GET /healthz` with 200 and the body
`ok` followed by a line feed. What it answers to another method on `/healthz`
is not specified by this version; the disk collector answers every method as
it does `GET`.

No relay calls `/v1/status` or `/healthz`. They can be reached only where a
collector listens for requests from others than its relay, which the disk
collector does not: it is served on the tunnel alone. `/v1/status` takes no
token (COLLIN-6), which is why it is specified only for a collector with one
session. What it answers on a collector that serves several is left to that
collector's side that faces its own clients (Scope and roles).

### The relay's side

**COLLIN-28.** The relay MUST fetch an input from the collector only when the
build asks it for one, and MUST read only a 200 as the input. Any other status,
or a request that fails, is the input's absence, which the relay reports to
the build as `relay-guest-api` specifies.

**COLLIN-29.** The relay MUST send a context path as the build gave it, with
its trailing `/` when it has one, under `/v1/context/`. It MUST read a 200
whose `Warden-Context` header is `list` as a listing, and any other 200 as a
file.

**COLLIN-30.** The relay MUST send `POST /v1/heartbeat`, with no body, on a
beat of 2 seconds: at each beat, one when the build's last activity is less
than 4 seconds old, and none when it is 5 seconds old or more. Between 4 and 5
seconds is the relay's choice, so that a relay may keep the time of the last
activity to the second, as the Go relay does. A beat may be late, or missed,
while the reply to the previous heartbeat is awaited (COLLIN-33). Activity is
the build's own heartbeat or a request the relay proxies for it
(`relay-guest-api`).

**COLLIN-31.** The relay MUST send `POST /v1/ready`, with no body, once,
before it answers the claim (`relay-claim`, Ordering).

**COLLIN-32.** The relay MUST send `POST /v1/complete` with the
`Content-Type` `application/json` and a body of the three members of
COLLIN-23 when the build signals its end, its `exit_code` being the code the
build gave. A relay MAY send a completion again each time the build signals
its end again, as the Go relay does; only the first is the build's result
(COLLIN-24).

**COLLIN-33.** The relay MUST read 200 or 204 to a signal as the signal
delivered. A signal that is not delivered MUST NOT fail the claim or the
build: the relay logs it and goes on. The relay MUST bound how long it waits
for a signal's reply.

**COLLIN-34.** The relay MUST NOT depend on the reply to `POST /v1/complete`:
the collector may close the session's connection before it replies
(COLLIN-2).

## Ordering

The order of a session, as the relay sends it: the ledger request is opened
first (`collector-outputs`, Ordering); `POST /v1/ready` is sent before the
claim is answered (COLLIN-31); the inputs are fetched as the build asks for
them, and heartbeats sent while it is active; and the first
`POST /v1/complete` is sent once the ledger request is done (COLLIN-35). A
heartbeat, or a later completion (COLLIN-32), may still follow it, and the
collector owes the relay nothing for either (COLLIN-2).

**COLLIN-35.** The relay MUST send `POST /v1/complete` only after its ledger
request has been answered or has failed (`collector-outputs`, Ordering).

**COLLIN-36.** A collector MUST answer the session's requests in any order
the relay sends them before its completion, inputs and signals while the
ledger request is open among them.

## Errors

A collector's replies, by status. Each is stated by the requirements named.

| Status | When | Requirements |
|---|---|---|
| 200 | The input, the signal received, the status, the health | COLLIN-13, COLLIN-14, COLLIN-16, COLLIN-17, COLLIN-21 to COLLIN-24, COLLIN-26, COLLIN-27 |
| 400 | A completion whose body is not one | COLLIN-23 |
| 401 | A session's token is missing or wrong | COLLIN-5 |
| 403 | A context path that is not safe | COLLIN-15 |
| 404 | No build script, no bootstrap config, no context, or a context path that names nothing | COLLIN-13, COLLIN-14, COLLIN-18, COLLIN-19 |
| 405 | A method the endpoint does not take | COLLIN-20, COLLIN-25, COLLIN-26 |

But for the 401's (COLLIN-5), the body of a reply other than 200 is text for a
person, which this version does not specify and no relay reads. A path this
protocol does not specify is outside it. The disk collector answers 404 to one
under `/v1/`, but for `/v1/artifacts`, `/v1/captures` and `/v1/context` with no
trailing `/`, which it answers, before it looks at the token, with 307 and a
`Location` that is the same path with one.

## Limits

This version sets no limit on the size of an input that a collector serves.

**COLLIN-37.** A collector MAY end a session whose `POST /v1/ready` has not
arrived within a time of its own, and MAY end a session whose heartbeats
stop for longer than a time of its own once a first one has arrived. It MUST
NOT end a session for want of heartbeats before the first has arrived, since
a build may take long to start.

The kit's session, which `cmd/collector` and every BuildWarden driver run,
gives a relay 90 seconds from the start of the claim to report `ready`, and
a build 30 seconds of silence once its first heartbeat has arrived. Both are
the kit's; another collector chooses its own. The Go relay waits at most
15 seconds for a signal's reply and 5 minutes for an input.

## Versioning

This is version 1 of the protocol, the one whose paths start `/v1/`. A
release of this specification is a tag `collector-inputs/vX.Y.Z` of the
specifications repository, and its `CHANGELOG.md` says what each changed.
While the release is `v0.x.y`, this document is edited in place and may still
change incompatibly. From `collector-inputs/v1.0.0` on, version 1 changes only
compatibly, and an incompatible change is a new document, `v2.md`, with its
own paths. The schemas' `$id`s carry the document's version, `v1`, and not a
release's.

The part this document states alike with `collector-outputs` (the session,
the transport, authentication and the names in paths) changes in both
documents together, and is released as a new version of each.

## Conformance

A collector conforms to this specification when it meets the requirements
of the *collector* role:

- COLLIN-1, COLLIN-2, COLLIN-3, COLLIN-5, COLLIN-6, COLLIN-7, COLLIN-8,
  COLLIN-10 and COLLIN-11;
- COLLIN-13 to COLLIN-27;
- COLLIN-36 and COLLIN-37.

COLLIN-26 binds a collector that serves one session; COLLIN-6 and COLLIN-27
bind one that can be reached by others than its relay, and a collector whose
target file says it cannot is not tested on them.

A relay conforms to this specification when it meets the requirements of the
*relay* role: COLLIN-4, COLLIN-9, COLLIN-12 and COLLIN-28 to COLLIN-35.

A requirement that no case of this specification's suite checks is listed,
with the reason, in [`not-machine-checked.txt`](not-machine-checked.txt).

## Known divergences

Where the reference implementation differs from a rule or a comment of its
own repository, or from the rest of this protocol. Each is what the code on
`main` does, and this document allows it; none is to be relied on. The
numbers are those of the design that wrote this specification.

### D1, the status takes no token

The disk collector serves `GET /v1/status` without the session's token,
where its package comment says that every endpoint but `/healthz` requires
one. COLLIN-6 states what the code does. Since the status names no session,
it is specified for a collector with one session only (COLLIN-26).

### D16, a completion whose reply may not come

The disk collector records a completion before it replies to it, and
`cmd/collector`, which has its result once the completion is recorded, closes
the tunnel at once. The relay can then see its `POST /v1/complete` fail, for
a build that completed, and logs it. COLLIN-23 has a 200 for a completion;
COLLIN-2 allows the collector to close first, and COLLIN-34 has the relay not
depend on the reply. A suite sends nothing it needs answered after a
completion.

<!-- collector-common: begin -->
### D8, the token with no scheme

COLLIN-7 asks a collector to accept `Authorization: Bearer <token>`, which is
the header every relay sends (COLLIN-9). The disk collector also accepts the
token with no scheme: it removes exactly `Bearer ` from the front of the
header when it is there, and compares what is left with the token. So
`Authorization: <token>` passes, while `bearer <token>` and `Bearer  <token>`,
with two spaces, do not. The Go relay's claim endpoint accepts the same bare
token in its own way (`relay-claim`, Known divergences), and the two differ
from each other in what spacing they take. A suite does not assert which
scheme a collector accepts beyond COLLIN-7.
