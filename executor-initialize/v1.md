# executor-initialize, version 1

How the executor's `initialize` is invoked and what it does before the build script runs.

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY" and "OPTIONAL" in this
document are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174)
when, and only when, they appear in all capitals. A requirement is a
paragraph or list item that starts with its identifier in bold.

## Scope and roles

A build runs in a *build environment* whose only network path is a relay.
The executor is the one program the host puts into that environment outside
the relay; everything else it needs, it fetches through the relay. This
document specifies the executor's command line, the steps its `initialize`
takes from its start to the build script's exit, and the three other
subcommands a build script may call.

Two roles:

- The *launcher* starts the executor in the build environment, once, through
  the environment's own boot mechanism or entrypoint. It is a driver's: in
  buildwarden/buildwarden, the container driver's entrypoint, cloud-init's
  `runcmd`, the Windows `warden-run` task and the macOS launchd daemon. How
  the launcher delivers the executor, and how it gives the environment its
  address, are not specified here; buildwarden/buildwarden's bootstrap model
  (BOOT-02, BOOT-03 there) governs them.
- The *executor* runs `initialize`. The reference executor is `warden-io`.

The executor is the client of the relay's guest API, which `relay-guest-api`
specifies: this document states which of its requests the executor makes,
in what order, and what it does with each reply, and not what the relay
answers. The bootstrap config the executor reads is specified by
`bootstrap-config`; this document states when the executor reads it and how
it applies the trust mode on each guest operating system.

The executor runs on three guest operating systems: Linux, macOS and
Windows. A requirement that names one of them holds on that one only;
"POSIX guests" means Linux and macOS. The executor runs with the rights to
write the guest's system trust store and its files under `/etc` (on Windows,
`%ProgramData%` and the hosts file).

This specification has no suite yet: its cases are for the item that
changes the executor's `initialize` (see Conformance).

## Transport

**INIT-1.** Every request the executor makes in `initialize`, and in the
subcommands of "The other subcommands", MUST go to the relay over plain
HTTP/1.1: to the reserved host `artifacts` or `cwd` on port 80, or to the
gateway's address on port 8300. The executor opens no other connection.

The reserved names reach the relay through the guest's resolver, which the
network step points at the gateway (INIT-12 to INIT-14), or, on Windows,
through the hosts file. The requests themselves, and the relay's replies,
are those of `relay-guest-api`: its reserved host `artifacts`, its reserved
host `cwd` and its control plane on port 8300.

## Messages and fields

### The invocation

**INIT-2.** A launcher MUST start the executor as
`<executor> initialize [<flag> ...]`. The executor MUST accept `init` as
the same subcommand.

**INIT-3.** The executor MUST accept these flags, each value flag both as
`--flag=value` and as `--flag value`. A flag given more than once takes its
last value.

| Flag | Value | Meaning |
|---|---|---|
| `--gateway` | The relay's IPv4 address on the build link | Where the executor reaches the relay's control plane, and where it points the guest's DNS |
| `--ip` | The build's own IPv4 address, `<address>/<prefix length>` | Used on Windows only (INIT-14) |
| `--script` | A file name | The name the build script is saved under, which picks its interpreter (INIT-30). Only its last path element is used |
| `--workdir` | A path | The directory the build script runs in: created with its parents and entered before the script is fetched |
| `--hold` | None | Stop after setup and wait, for an interactive shell (INIT-32, INIT-33) |

**INIT-4.** When `--gateway` is absent or its value is empty, the executor
MUST take the gateway from the environment variable `WARDEN_GATEWAY`; when
`--ip` is absent or empty, it MUST take the build's address from
`WARDEN_IP`.

**INIT-5.** A launcher MUST give the executor the gateway, by `--gateway`
or `WARDEN_GATEWAY`. Every launcher of the reference implementation passes
`--gateway`. An executor started with no gateway does not reach the relay
(Known divergences, D12).

**INIT-6.** The executor MUST ignore an argument of `initialize` that is
none of the flags of INIT-3, and a value flag that is the last argument
and so has no value (Known divergences, D14).

**INIT-7.** When `--script` is absent or empty, the executor MUST use the
default script name: `build.sh` on POSIX guests and `build.ps1` on Windows.

**INIT-8.** When `--workdir` is absent or empty, the build script MUST run
in the executor's own working directory.

### The requests

The executor makes these requests of the relay, in the order of Ordering.
Each is a request of `relay-guest-api`.

| Step | Request | Reply the executor accepts | Any other reply, or no reply |
|---|---|---|---|
| Wait for the relay | `GET http://<gateway>:8300/health` | `200` | Retried until the wait ends (INIT-17) |
| The CA | `GET http://artifacts/ca.pem` | `200` with a PEM certificate | `initialize` stops (INIT-43) |
| The bootstrap config | `GET http://artifacts/bootstrap` | `200` with a config `bootstrap-config` accepts, or `404` | `initialize` stops (INIT-43) |
| The build script | `GET http://artifacts/build-script` | `200` | `initialize` stops (INIT-43) |
| The build's output | `POST http://<gateway>:8300/v1/output` | `200` | The executor stops sending output (INIT-44) |
| Heartbeat | `GET http://artifacts/heartbeat` | Any | Ignored |
| Exit | `POST http://artifacts/exit?code=<n>` | Any | Ignored |

**INIT-9.** The executor MUST accept the CA only when
`http://artifacts/ca.pem` is answered `200` and the body's first PEM block
is an X.509 certificate. It MUST use the body exactly as served wherever it installs
or names the CA in PEM form.

**INIT-10.** The executor MUST read the bootstrap config as
`bootstrap-config` specifies: a `404` is the empty config, whose trust mode
is `append`, and a `200` body is parsed under that document's rules for an
executor.

**INIT-11.** The executor MUST send `POST http://artifacts/exit?code=<n>`
with an empty body, `<n>` the decimal exit code of INIT-38.

### The network step

The network step points the guest's name resolution at the relay, so that
the reserved names `artifacts` and `cwd`, and every other name the build
looks up, are answered by the relay. With no gateway (INIT-5) the executor
takes no network step.

**INIT-12.** On Linux the executor MUST replace `/etc/resolv.conf` with the
one line `nameserver <gateway>`. A failure to write it MUST stop
`initialize` (INIT-43).

**INIT-13.** On macOS the executor MUST write `nameserver <gateway>` to
`/etc/resolver/artifacts`, `/etc/resolver/cwd` and `/etc/resolv.conf`, and
MUST set the gateway as the DNS server of the service
`State:/Network/Service/warden/DNS` through `scutil`, with an empty
supplemental match domain. A failure of any of these MUST NOT stop `initialize`.

**INIT-14.** On Windows the executor MUST map `artifacts` and `cwd` to the
gateway in the hosts file (`%SystemRoot%\System32\drivers\etc\hosts`), each
on a line that ends with the marker `# warden-io`, removing every line that
carries the marker first and keeping every other line. Then, with a build
address, it MUST give the first physical interface that is up (or, failing
one, the first interface) that address with its prefix length (`24` when
the value has none), a default route through the gateway and the gateway
as its DNS server; with no build address, it MUST set the gateway as the
DNS server of every interface. A failure of any of these MUST NOT stop
`initialize`.

**INIT-15.** On POSIX guests the executor MUST NOT change the build's
interface address: the launcher, or the relay's DHCP lease, gives it. The
executor accepts `--ip` and `WARDEN_IP` there and does not use them.

### Waiting for the relay

**INIT-16.** The executor MUST wait for the relay before its first other
request: it requests `GET http://<gateway>:8300/health` until one is
answered `200`.

**INIT-17.** The wait MUST poll every 500 ms, each attempt limited to 2 s,
and MUST end after 60 s without a `200`; `initialize` then stops
(INIT-43). On Windows the error then names each IPv4 address of the guest
other than loopback with its origin, and says of a self-assigned
`169.254.0.0/16` address that the interface got no DHCP lease from the
relay.

### Trust

The executor installs the relay's CA in the guest's system trust store, by
the trust mode of the bootstrap config (`bootstrap-config`): `append` adds
the CA to the system's roots; `exclusive` makes it the only one.

**INIT-18.** On Linux the executor MUST write the CA to
`/usr/local/share/ca-certificates/warden-ca.crt` in both modes.

**INIT-19.** On Linux, with `exclusive`, the executor MUST replace the
directory `/etc/ssl/certs` with one holding only `warden.crt` and
`ca-certificates.crt`, both the CA, and the symbolic link
`<subject hash>.0` to `warden.crt`, where the subject hash is OpenSSL's
(`openssl x509 -subject_hash`); MUST replace with the CA each of
`/etc/pki/tls/certs/ca-bundle.crt`,
`/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem` and `/etc/ssl/cert.pem`
that exists; and MUST install the hook
`/etc/ca-certificates/update.d/99warden`, which restores the same state
when the build reinstalls its certificates. A failure of any of these MUST
stop `initialize`.

**INIT-20.** On Linux, with `append`, the executor MUST run
`update-ca-certificates` when it is on the `PATH`. When it is absent or
fails (a failure is reported on stderr), the executor MUST append a newline
and the CA to the first of `/etc/ssl/certs/ca-certificates.crt`,
`/etc/pki/tls/certs/ca-bundle.crt` and `/etc/ssl/cert.pem` that it can open
for writing. When it can open none, `initialize` MUST stop.

**INIT-21.** On macOS the executor MUST add the CA to
`/Library/Keychains/System.keychain` as a trusted root
(`security add-trusted-cert -d -r trustRoot`, from a copy it writes to
`/tmp/warden-ca.pem` and removes afterwards), reporting a failure on
stderr and going on, and MUST write `/etc/ssl/cert.pem` as its previous
content (none if it did not exist), a newline and the CA. A failure to
write the copy or `/etc/ssl/cert.pem` MUST stop `initialize`.

**INIT-22.** On Windows the executor MUST write the CA to
`<data directory>\warden-ca.pem` and MUST import it into the machine's
`Root` store (`certutil.exe -addstore -f Root <file>`), reporting a failure
of the import on stderr and going on. A failure to write the file MUST stop
`initialize`.

**INIT-23.** On macOS and Windows the executor MAY receive `exclusive`; it
then MUST say on stderr that exclusive trust is not supported on that
system and MUST install the CA as for `append`.

### The baseline

The baseline is what the executor sets up in every build environment from
the CA alone. It is not configurable (BOOT-05 in buildwarden/buildwarden):
no flag, variable or field of the bootstrap config changes it.

**INIT-24.** The *data directory* MUST be `/etc/warden` on POSIX guests,
and on Windows `%ProgramData%\warden` (`C:\ProgramData\warden` when
`ProgramData` is not set).

**INIT-25.** The executor MUST set these variables in the build script's
environment:

| Variable | Value |
|---|---|
| `SOURCE_DATE_EPOCH` | `0` |
| `UV_NATIVE_TLS` | `1` |
| `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `NODE_EXTRA_CA_CERTS`, `PIP_CERT`, `CARGO_HTTP_CAINFO`, `NIX_SSL_CERT_FILE`, `HEX_CACERTS_PATH` | The CA bundle's path (INIT-26), each only when there is one |
| `MAVEN_OPTS`, `GRADLE_OPTS` | `-Djavax.net.ssl.trustStore=<truststore> -Djavax.net.ssl.trustStorePassword=changeit` |

`<truststore>` is the Java truststore's path (INIT-27) with `/` as its
separator on every system.

**INIT-26.** The CA bundle MUST be looked up after the CA is installed: on
Linux the first of `/etc/ssl/certs/ca-certificates.crt`,
`/etc/pki/tls/certs/ca-bundle.crt` and `/etc/ssl/cert.pem` that exists; on
macOS `/etc/ssl/cert.pem` if it exists; on Windows
`<data directory>\warden-ca.pem`, which holds the CA alone, if it exists.

**INIT-27.** The executor MUST write a Java truststore to
`<data directory>/certs.jks`: a JKS keystore, version 2, holding one
trusted-certificate entry, the CA under the alias `warden` of type `X.509`,
with the CA's `NotBefore` in milliseconds as its creation time and the
password `changeit`. The same CA MUST give the same bytes.

**INIT-28.** The executor MUST write the system Bazel configuration, at
`/etc/bazel.bazelrc` on POSIX guests and on Windows at `bazel.bazelrc` in
the data directory's parent (`%ProgramData%\bazel.bazelrc`), as the one
line
`startup --host_jvm_args=-Djavax.net.ssl.trustStore=<truststore> --host_jvm_args=-Djavax.net.ssl.trustStorePassword=changeit`.

**INIT-29.** The build script MUST inherit the executor's environment with
the baseline's variables set, so that the script's own assignments override
them, and with the directory that holds the executor put first on its
`PATH` (the variable found without regard to case, joined with the
system's list separator, and set to that directory alone when there is
none).

### The build script

**INIT-30.** The executor MUST save the build script as
`<temporary directory>/<script name>`, in the operating system's temporary
directory as the system reports it (on POSIX guests `$TMPDIR`, or `/tmp`
when it is unset; on Windows the one `GetTempPath` gives, `%TMP%` or
`%TEMP%` first), make
it executable where the system has the mode, and run it with the
interpreter its name selects:

| Guest | Script name | Command |
|---|---|---|
| POSIX | Any | `/bin/bash <file>` when `/bin/bash` exists, otherwise `/bin/sh <file>` |
| Windows | Ending in `.cmd` or `.bat`, in any case | `cmd.exe /c <file>` |
| Windows | Any other | `powershell.exe -NoProfile -ExecutionPolicy Bypass -File <file>` |

**INIT-31.** The build script MUST run with the executor's standard input,
in the directory of INIT-8 or `--workdir`. Its standard output and standard
error MUST be one stream, written to the executor's standard output (the
console) and sent to the relay as the build's output (INIT-40).

### Holding for a shell

**INIT-32.** With `--hold`, the executor MUST take every step up to and
including entering the work directory (Ordering), then MUST NOT fetch or
run the build script, send output or heartbeats, or report an exit.

**INIT-33.** With `--hold`, the executor MUST write
`<data directory>/shell.env` and then wait until the build environment is
torn down. The file is a POSIX shell script: one line
`export <name>='<value>'` for each variable of the baseline, in byte order
of the names, the value quoted for the shell, and for `PATH` the
executor's directory and the executor's own `PATH`, joined with the
system's list separator; then, when a
work directory was given, `cd '<work directory>'`. Its appearance tells
whoever holds the session that setup is done.

### The other subcommands

A build script reaches the relay's guest API through these, as well as by
its own requests.

**INIT-34.** `<executor> fetch <path> ... [-o <destination>]` MUST fetch
each path from the build context, `GET http://cwd/<path>`, accepting only
`200`. A path that ends with `/`, or that is `.` (the context's root),
names a directory: the executor MUST first fetch its listing,
`GET http://cwd/<path>` (for `.`, `http://cwd/`), whose non-empty lines are
file paths relative to the context's root, and then each of those files,
stopping at the first that fails. The destination of a file is: with no
`-o`, the path itself, relative to the working directory; with `-o`, for a
directory's file `<destination>/<its path less the directory's>`, and for a
named file `<destination>` when exactly one path is given and
`<destination>` does not end with `/`, and `<destination>/<its last path
element>` otherwise. The executor MUST create the destination's missing
directories, MUST go on to the next path after a failed one, and MUST exit
with status 1 if any path failed and 0 otherwise. With no path, or `-o`
with no value, it MUST exit with status 1.

**INIT-35.** `<executor> post <file> [<name>]` MUST send the file's bytes
as `POST http://artifacts/<name>` with `Content-Type:
application/octet-stream`, `<name>` being the file's last path element when
it is not given. On `200` it MUST write the reply's body to standard output
and exit with status 0; otherwise it MUST write the status and the body to
standard error and exit with status 1.

**INIT-36.** `<executor> trust` MUST fetch the CA as INIT-9 does and
install it as for `append`, whatever the build's bootstrap config, and
exit with status 0, or 1 when either fails.

**INIT-37.** The executor MUST print its usage to standard error and exit
with status 1 when it is given no subcommand or one it does not know.

### Exit

**INIT-38.** The exit code of a build is the build script's: its exit
status when it exits; `-1` when, on a POSIX guest, it is ended by a signal;
and `1` when it cannot be started. The executor MUST report it to the
relay (INIT-11) and MUST then exit with the same code (a code of `-1`
gives the process status 255 on POSIX guests).

## Ordering

**INIT-39.** `initialize` MUST take its steps in this order, each only once
the one before it has succeeded:

1. The network step (INIT-12 to INIT-14).
2. The wait for the relay (INIT-16).
3. `GET http://artifacts/ca.pem`.
4. `GET http://artifacts/bootstrap`.
5. The CA's installation, by the config's trust mode (INIT-18 to INIT-23).
6. The baseline (INIT-24 to INIT-28).
7. The work directory, created and entered.
8. With `--hold`, the shell's environment and the wait (INIT-33); nothing
   follows.
9. `GET http://artifacts/build-script`, saved (INIT-30).
10. The build script, run (INIT-31), with its output (INIT-40) and the
    heartbeats (INIT-41).
11. Once the script has exited and its output has been sent or abandoned,
    `POST http://artifacts/exit?code=<n>` (INIT-11).
12. The executor's exit (INIT-38).

**INIT-40.** While the build script runs, the executor MUST send its output
to the relay as it is produced, in order, in chunks of at most 32 KiB, as
the bodies of `POST http://<gateway>:8300/v1/output` with `Content-Type:
text/plain`, one request at a time; the script's writes wait while a chunk
is being sent. Chunk boundaries carry no meaning.

**INIT-41.** While the build script runs, the executor MUST send
`GET http://artifacts/heartbeat` every 2 s, the first 2 s after the script
starts, and MUST stop when the script exits.

**INIT-42.** The executor MUST send the exit report only after the last
chunk of output has been answered or abandoned (INIT-44), so that the
relay has the build's whole output before its completion.

## Errors

**INIT-43.** A failure in a step before the build script runs (the network
step on Linux, the wait for the relay, the CA, the bootstrap config, the
CA's installation, the baseline, the work directory, the build script's
fetch or the shell's environment) MUST end `initialize` with a line
`warden-io: <step>: <error>` on standard error and the process status 1.
The executor sends no exit report then, and the relay receives no
completion (Known divergences, D13).

**INIT-44.** When a chunk of output fails (the request fails, takes more
than 30 s, or is answered other than `200`), the executor MUST stop sending
output, MUST say so once on standard error, and MUST go on reading and
discarding the script's output, which still reaches the console, so that
the build neither fails nor waits on the relay.

**INIT-45.** The executor MUST NOT let a failed heartbeat or a failed exit
report change the build: a heartbeat's failure is ignored, and the executor
exits with the build's code whether or not the exit report was answered.

## Limits

| What | Limit |
|---|---|
| The wait for the relay | 60 s, polled every 500 ms, each attempt 2 s (INIT-17) |
| A chunk of output | 32 KiB, each request 30 s (INIT-40, INIT-44) |
| Heartbeats | One every 2 s, each request 2 s (INIT-41) |
| The CA, the bootstrap config, the build script, the exit report, `fetch` and `post` | No time limit and no size limit set by the executor |

The relay's own limits on what it serves and accepts, the 256 MiB of a
build's output among them, are `relay-guest-api`'s.

## Versioning

`v1.md` is version 1 of this contract. While this specification's releases
are `v0.x.y`, the document is edited in place and may still change
incompatibly; from `executor-initialize/v1.0.0` on, version 1 changes only
compatibly, and an incompatible change is a new document `v2.md`.

The command line carries no version. A launcher can tell which executor it
starts only by delivering it itself, which buildwarden/buildwarden's
bootstrap model requires: the executor is delivered per build and matches
the orchestrator's version (BOOT-02 there). Within version 1 a new flag is
optional: an executor that predates it ignores it (INIT-6), so a launcher
that needs it to take effect must deliver an executor that has it.

The guest API the executor calls carries no version beyond the `/v1/` of
its control-plane paths (`relay-guest-api`). The item that moves trust-store
generation out of `initialize` (S2 of the componentization program in
buildwarden/buildwarden) adds the version through which the executor and
the relay agree, and this document's next version with it.

## Conformance

An executor conforms to this version when it meets every requirement of
the executor: INIT-1, INIT-2 (the subcommand and its alias), INIT-3,
INIT-4, INIT-6 to INIT-45, those that name a guest operating system for the
systems it runs on. An executor for an operating system this document does
not name states which system's requirements it meets in their place.

A launcher conforms to this version when it meets INIT-2 and INIT-5, and
on POSIX guests gives the build environment its address before it starts
the executor (INIT-15).

This specification has no suite: every requirement is listed in
`not-machine-checked.txt`, because the executor's cases are for the item
that changes what `initialize` does (S2 of the componentization program).
Until then the reference executor is held to this document by its own Go
tests in `cmd/warden-io/`. What the relay answers to the executor's
requests is checked by the suite of `relay-guest-api`, and what it serves
as the bootstrap config by that of `bootstrap-config`.

## Known divergences

Places where the reference implementation differs from a rule or a comment
of its own repository, or from the rest of this protocol. Each is what the
code does, and the requirements above allow it where they name it. The
numbers are those of the design that wrote this document,
`docs/design/seam-specs.md` in buildwarden/buildwarden, under "Divergences
found".

### D12: no gateway, no relay

With no `--gateway` and no `WARDEN_GATEWAY`, `warden-io` takes no network
step and waits for the relay at `http://artifacts/health`, which the relay
does not serve (it answers `404`, `relay-guest-api`). The wait therefore
ends after 60 s and `initialize` stops. This differs from the executor's own
code, which has the path as the way to reach a relay without a gateway.
Every launcher passes `--gateway` (INIT-5), so no build takes the path.

### D13: a failure before the script is not reported

A failure in any step before the build script runs (INIT-43) ends
`warden-io` with status 1 and no exit report, so the relay sends no
completion and the collector learns of the failure only by its own limits
on the session (`collector-inputs`). This differs from EXEC-02 in
buildwarden/buildwarden: failures "produce a structured exit reported back
through the relay, never a silent death". A script that cannot be started
is reported (INIT-38).

### D14: an unknown flag is ignored

`warden-io initialize` ignores an argument it does not know, and a value
flag given last with no value (INIT-6), where GLOBAL-10 in
buildwarden/buildwarden asks that a provided value that cannot be used be
an error. A misspelt `--gatway=...` therefore takes effect as no gateway at
all (D12).
