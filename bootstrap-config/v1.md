# bootstrap-config, version 1

The policy document a collector serves and the executor reads through the relay.

| | |
|---|---|
| Seam | 6, the bootstrap config |
| Requirement identifiers | `BOOTCFG-<n>` |

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY" and "OPTIONAL" in this
document are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174)
when, and only when, they appear in all capitals. A requirement is a
paragraph or list item that starts with its identifier in bold.

## Scope and roles

The bootstrap config is the one decision about a build environment's setup
that the host makes and sends through the relay: the trust policy for the
guest's system trust store. Everything else the executor sets up it derives
from the relay's CA itself (`executor-initialize`, its baseline). The config
carries policy only: no path, no file content, no command and no environment
variable (BOOT-05 in buildwarden/buildwarden).

Three roles:

- The *producer* supplies a build's config to the collector, with the
  build's other inputs. In buildwarden/buildwarden the producer is the
  claimant's session (`driver.Session`), which starts the collector with it.
- The *relay* carries the config from the collector to the build
  environment, and records it.
- The *executor* reads the config and applies it. The reference executor is
  `warden-io`'s `initialize`.

This document specifies the config's form, what the relay does with it, and
how an executor reads it. The requests that carry it are specified by
`collector-inputs` and `relay-guest-api`; when the executor reads it, and
how it installs the CA on each guest operating system, by
`executor-initialize`.

## Transport

The config is the body of two requests, both `GET`, both answered
`application/json`:

- `GET /v1/bootstrap` on the collector, made by the relay
  (`collector-inputs`); `404` when the build has no config.
- `GET http://artifacts/bootstrap` on the relay, made by the executor
  (`relay-guest-api`).

**BOOTCFG-1.** For each `GET http://artifacts/bootstrap` a relay MUST
request `GET /v1/bootstrap` of the build's collector and, when it is
answered `200`, MUST answer `200` with `Content-Type: application/json` and
the collector's body, byte for byte. The relay MUST NOT parse, check or
change the body: it carries a document this version would reject as it
carries one it accepts.

**BOOTCFG-2.** A relay MUST record each body it serves under BOOTCFG-1 in
its ledger, as an input served to the build, the way it records the build
script (`relay-guest-api`).

**BOOTCFG-3.** When the collector answers `GET /v1/bootstrap` other than
`200`, or cannot be reached, a relay MUST answer
`GET http://artifacts/bootstrap` with `404` and record nothing. To the
executor that is the empty config (BOOTCFG-10).

## Messages and fields

### The document

```json v1.schema.json
{"version": 1, "trust": {"mode": "exclusive"}}
```

| Member | Type | Meaning |
|---|---|---|
| `version` | integer, required | The config format's version: `1` |
| `trust` | object, optional | The system trust policy |
| `trust.mode` | string, optional | `append` or `exclusive` |

**BOOTCFG-4.** A producer MUST supply a document that (a) validates
against `v1.schema.json`: one JSON object with the member `version`, whose
value is `1`, and optionally the member `trust`, an object with optionally
the member `mode`, `append` or `exclusive`, and no other member at either
level; and (b), beyond what the schema expresses, is written in UTF-8 with
no byte order mark, writes `version` as the token `1`, and has no member
twice. The schema passes `{"version": 1.0}` and `{"version": 1e0}`, which
are the integer 1 under JSON Schema and which an executor rejects
(BOOTCFG-12), and it cannot see a byte order mark or a member given twice:
a check of a producer checks (b) apart from the schema.

**BOOTCFG-5.** A producer MAY supply no document for a build. The
collector then answers `GET /v1/bootstrap` with `404` (`collector-inputs`),
and the build gets the empty config.

**BOOTCFG-6.** The document a producer supplies for a build MUST be the
same for the whole of the build's session: every `GET /v1/bootstrap` of the
session is answered with the same bytes.

A document with no `trust`, or a `trust` with no `mode`, has the mode
`append`:

```json v1.schema.json
{"version": 1}
```

### The trust modes

**BOOTCFG-7.** An executor MUST apply the document's trust mode to the
guest's system trust store: with `append` it adds the relay's CA to the
system's roots and keeps the others; with `exclusive` the relay's CA
becomes the system's only root, so that no connection the build makes can
be validated by any other root. How it does so on each guest operating
system is `executor-initialize`'s.

**BOOTCFG-8.** An executor whose guest operating system has no procedure
for `exclusive` MAY apply `append` in its place, and MUST then say so in
its output. The reference executor does so on macOS and Windows
(`executor-initialize`).

`exclusive` is the stronger policy: every TLS connection from the build
goes through the relay, which presents its own leaves, so no other root can
validate a real connection, and a root that could would only let a
connection bypass the record.

### The reference producer's policy

The producer in buildwarden/buildwarden (`bootstrap.ForGuest`) sends
`{"version":1,"trust":{"mode":"exclusive"}}` for a Linux guest (and for a
guest it is not told the system of, or one it does not know), and
`{"version":1,"trust":{"mode":"append"}}` for a Windows or macOS guest. That
choice is the reference producer's policy, stated here as such; this
document requires it of no producer.

### How an executor reads it

**BOOTCFG-9.** An executor MUST read the config from
`GET http://artifacts/bootstrap`, once for each build, at the point
`executor-initialize` gives.

**BOOTCFG-10.** An executor MUST take as the empty config, whose trust
mode is `append`, a `404`, and a `200` whose body is empty or holds only
JSON white space.

**BOOTCFG-11.** An executor MUST stop, and not set up the build, when the
request fails or is answered with a status other than `200` and `404`.

**BOOTCFG-12.** Except as BOOTCFG-14 allows, an executor MUST reject a
`200` body, and stop, when the body is not one JSON object (`null` among them); when a member's value has
the wrong type (`version` not an integer written with no fraction or
exponent, `trust` not an object or `null`, `mode` not a string or `null`);
when the object has a member other than `version` and `trust`, or `trust`
one other than `mode`; when a second JSON value follows the object; when
`version` is absent or not `1`; or when `mode` is a string other than
`append`, `exclusive` and the empty string, compared with case. It MUST NOT
fall back to a default for a document it rejects: an executor never
guesses at a newer config.

**BOOTCFG-13.** An executor MUST read a `trust` that is absent, `null` or
an empty object, and a `mode` that is absent, `null` or the empty string,
as the mode `append`.

**BOOTCFG-14.** An executor MAY read a `200` body more loosely than
BOOTCFG-10 and BOOTCFG-12 in these four ways, and in no other: it MAY match
the member names of BOOTCFG-12 without regard to case (under Unicode simple
case folding, so that `VERSION` and `verſion` are `version`); MAY merge a
member given twice into the first, the later value decoded onto the
earlier, so that a later `null` leaves the earlier value as it was and a
later `trust` object changes only the members it has; MAY ignore
everything from a `}` or a `]` that follows the object, to the body's end;
and MAY take as the empty config a body that holds only white space in
Unicode's sense (form feed, vertical tab, U+0085, U+00A0 and U+2028 among
it), not only JSON's. The reference executor does all four (Known
divergences, N1); a producer that meets BOOTCFG-4 sends none of them.

## Ordering

The producer supplies the config before the build starts: the reference
producer gives it to the collector when it starts the collector, before the
claim. The relay fetches it from the collector only when the executor asks
for it (BOOTCFG-1). The executor reads it after the relay's CA and before
it installs the CA (`executor-initialize`, its order of steps).

## Errors

| Who | Condition | What follows |
|---|---|---|
| Relay | The collector answers other than `200`, or cannot be reached | `404` to the executor (BOOTCFG-3) |
| Executor | `404`, or an empty body | The empty config: `append` (BOOTCFG-10) |
| Executor | Any other status, or a failed request | The executor stops (BOOTCFG-11) |
| Executor | A body BOOTCFG-12 rejects | The executor stops |

How an executor stops, and what it reports, is `executor-initialize`'s.

## Limits

This version sets no limit on the document's size; a conforming document
is a few dozen bytes. A relay's limit on what it reads from the collector
for any input is `relay-guest-api`'s.

## Versioning

The document carries its own version in `version`, and an executor rejects
a version it does not know (BOOTCFG-12), so that it never applies half of a
newer policy. While this specification's releases are `v0.x.y`, this
document is edited in place and may still change incompatibly; from
`bootstrap-config/v1.0.0` on, version 1 changes only compatibly.

Because an executor rejects a member it does not know (BOOTCFG-12), version
1 gains no member and no trust mode: a new member or mode is version 2, in
a new document `v2.md`, with `version` `2`. A producer whose executors may
predate it sends version 1. Every version carries policy only, as version 1
does (Scope and roles).

## Conformance

A producer conforms to this version when it meets BOOTCFG-4 to BOOTCFG-6.

A relay conforms to this version when it meets BOOTCFG-1 to BOOTCFG-3.

An executor conforms to this version when it meets BOOTCFG-7 and BOOTCFG-9
to BOOTCFG-13, and BOOTCFG-8 where it applies `append` in place of
`exclusive`.

The suite checks the relay against BOOTCFG-1 to BOOTCFG-3 and the producer
against the document it serves. It runs no executor: the requirements of
the executor are listed in `not-machine-checked.txt`, because the
executor's cases are for the item that changes what `initialize` does (S2
of the componentization program in buildwarden/buildwarden). Until then the
reference executor is held to them by the Go tests of `bootstrap/` and
`cmd/warden-io/` there.

## Known divergences

Places where the reference implementation differs from a rule or a comment
of its own repository, or from the design that wrote this document,
`docs/design/seam-specs.md` in buildwarden/buildwarden. Each is what the
code does, and the requirements above allow it where they name it. The
design's table, under "Divergences found", holds D1 to D19 and N1 to N33;
of those, the two below concern this seam. The N numbers are shared by the
six documents: N24 is recorded in `relay-guest-api` too.

### N1: the reference executor reads more loosely than strictly

The design (seam 6: "Reading is strict: an unknown field, trailing data
... is an error") and `bootstrap.Parse`'s own comment ("decodes and
validates a config strictly", `bootstrap/bootstrap.go:67`) have the
executor's reading strict. `bootstrap.Parse` accepts four kinds of body
that a strict reading rejects, which BOOTCFG-14 allows:

- Member names matched without regard to case:
  `{"VERSION":1,"Trust":{"MODE":"exclusive"}}` is read as `exclusive`.
  `encoding/json` matches names so (`bootstrap/bootstrap.go:75-77`).
- A member given twice merged into the first:
  `{"version":2,"version":1}` is accepted as version 1, and
  `{"version":1,"trust":{"mode":"exclusive"},"trust":null}` and
  `...,"trust":{}}` are read as `exclusive`.
- Everything from a `}` or `]` that follows the object ignored:
  `{"version":1}]garbage` and `{"version":1}}{"version":2}` are read as
  the version-1 empty config. The check for trailing data,
  `dec.More()` (`bootstrap/bootstrap.go:80`), reports no more values at a
  `}` or `]`.
- A body of only Unicode white space read as the empty config: `\f`,
  `\v`, U+0085, U+00A0 and U+2028 alone are each `append`.
  `bytes.TrimSpace` (`bootstrap/bootstrap.go:72`) trims Unicode white
  space, not JSON's.

Seen by calling `bootstrap.Parse` from `origin/main` with each body; the
reviewer of this document also ran `warden-io initialize` against a relay
that served `200` with `\f` and with `{"version":1}]garbage`, and the
build script ran both times.

### N24: a collector's failure turns `exclusive` into `append`

The Go relay answers `404` to `GET http://artifacts/bootstrap` when the
collector's reply is not `200` or the request to it fails
(`relay/relay.go:732-738`, BOOTCFG-3), and an executor takes a `404` as the
empty config, whose mode is `append` (BOOTCFG-10). Each is as this
document states; together, a collector that fails while it holds an
`exclusive` config gives the build `append`, and the build trusts the
system's roots besides the relay's. This differs from GLOBAL-10 in
buildwarden/buildwarden, under which the default is not tried when a
provided value fails. The design's table holds it as a row of class (c),
its **Defaults and overrides** names it as a fallback of today's code that
the design neither adds nor allows, and its security note gives it a
security angle. The relay's half was run in this suite's stage against the
Go relay in host, vm and container mode: a collector that answered
`GET /v1/bootstrap` `500` while it held a config, and a request to the
collector that failed, each gave the build `404` and recorded nothing. The
executor's half, a `404` read as `append`, is read from the code.
